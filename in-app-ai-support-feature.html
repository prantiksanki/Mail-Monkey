Overview

What this feature is

A persistent support launcher docked in the corner of the app. One click opens a home panel with a personalized greeting and a short menu; from there users can read docs, check status, or start a chat that an AI agent picks up immediately — with a clean escalation path to a human when needed.

👋

Personalized home

Greets the signed-in user by name (“Hey Anish”) and presents Help centre, System status, Start a conversation, and past Conversations in one panel.

🤖

AI support agent

An AI agent (“Parker”) replies within seconds, answers product questions, and honors clear boundaries — it declines actions it can’t take and points users to the right tool instead.

🧵

Threaded conversations

Every chat is a stored, resumable ticket (e.g. T-6355) with unread counts, timestamps, and an offline notice showing when the team is back online.

Anatomy

How the widget is built up

Two screens do most of the work: a home panel for triage and a conversation view for the actual chat. Everything else is supporting state.

1 · Home panel

  • AGreeting header — brand mark, gradient banner, personalized “Hey {firstName}” line, close button.
  • BSelf-serve links — Help centre and System status open resources without contacting support.
  • CStart a conversation — the primary CTA, visually emphasized.
  • DConversations list — prior threads with an unread badge.

2 · Conversation view

  • AThread header — back arrow, ticket id, minimize / close.
  • BAvailability banner — “We’re currently offline. We’ll be back at 1:30 PM.”
  • CMessage stream — user vs. agent bubbles with avatars, sender name, relative time.
  • DComposer — rich input (bold, italic, code, attachments) with Ctrl + ↵ to send.
Agent guardrails matter. In the reference, when asked to “send an email,” Parker declines because it’s a support agent, not an actor on the user’s account — then redirects to the correct product surface. Our agent should behave the same way: answer support questions, refuse out-of-scope actions, and route users to the feature that does the job.

User Flow

From launcher to resolution

The happy path is four steps. A fifth, escalation, branches off whenever the AI can’t fully resolve the request.

1

Open

User taps the floating launcher; the home panel opens with their name and menu.

2

Triage

They self-serve via Help centre / Status, or hit “Start a conversation”.

3

Ask

The AI agent greets them and answers, respecting scope boundaries.

4

Resolve

Answer delivered, or handed to a human with full context preserved.

Scope

What the agent does — and doesn’t

Clear boundaries keep trust high and prevent the AI from taking risky actions on a user’s account.

Explain errors & billing basicsDiagnoses common issues; links to the right settings page.In scope
Check system / service statusSurfaces live status and incident notices.In scope

Under the hood

Architecture at a glance

A thin embeddable client, an API layer for conversations, and an AI orchestration service backed by a knowledge base.

🖥️

Client widget

Embeddable React component with a floating launcher, home + conversation views, local unread state, and a rich-text composer. Renders over the app; owns nothing sensitive.

🔌

Conversation API

oRPC protectedProcedure endpoints for creating tickets, streaming messages, and paginating threads with cursor-based pagination — Zod-validated in and out.

🧠

AI orchestration

Routes a message through the latest Claude model (claude-opus-4-8 / claude-sonnet-5) with a support system prompt, tool boundaries, and retrieval over the knowledge base.

🗄️

Persistence & status

Tickets, messages, and read state in the database via @repo/database; a status source drives the offline banner and “back at 1:30 PM” copy.

Implementation Plan

Phased rollout

Ship a usable slice early, then layer in intelligence and polish. Each phase is independently shippable behind a flag.

Phase 1Foundation

Widget shell & data model

  • Floating launcher + home panel with personalized greeting.
  • DB schema: ticket, message, read_state.
  • oRPC procedures to create a conversation and post messages.
Phase 2Conversations

Human-first chat

  • Conversation view, message stream, rich composer, unread badges.
  • Availability banner driven by support hours / status source.
  • Real-time updates (subscription or polling) and thread history.
Phase 3Intelligence

AI agent “Parker”

  • Knowledge-base retrieval + Claude-backed responses with guardrails.
  • Scope enforcement: decline actions, redirect to product surfaces.
  • Confidence-based escalation handing full context to a human.
Phase 4Polish & scale

Self-serve & insights

  • Help centre + System status integrations in the home panel.
  • Analytics: deflection rate, CSAT, unresolved topics.
  • Accessibility pass, i18n, and mobile layout hardening.

Success Metrics

How we’ll know it works

Support is a means to an end — users resolving their problem quickly. These are the signals to watch.

Deflection rate

Share of conversations resolved by the AI or self-serve links without a human — the core efficiency metric.

Time to first response

Should approach seconds for AI replies, well below any human queue time.

Resolution CSAT

Post-conversation satisfaction, split by AI-resolved vs. escalated to catch quality gaps early.

North star: a user with a question never has to leave the app, wait in a queue, or repeat themselves to a human. The widget meets them where they are, answers fast, and only involves a person when it genuinely helps.
