# CASA 5.1.9 — Data Validation and Sanitization: OS command injection protection

> **Control 5.1.9 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *Protect against OS command injections.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

No application code anywhere in this repository executes an OS command or
shell. There is no `child_process` usage, no `execFile`/`spawn` family call,
and no shell-out library in application code at all — the control is
satisfied by absence: with no OS command ever executed, there is no
command-injection surface to protect.

---

## Deliverable — evidence

### No process-spawning API used anywhere in application code

A repository-wide search across every `.ts`, `.tsx`, `.js`, and `.mjs` file
(excluding `node_modules`) for `child_process`, `execFile`/`execFileSync`,
`Bun.spawn`, `Deno.run`, `exec(`, and `spawn(` returned **zero matches**.
Every `package.json` in the monorepo (dependencies, not just
devDependencies) was also checked for shell-out libraries — `execa`,
`shelljs`, `cross-spawn`, `node-pty` — with the same result: none are used by
application code.

### Free-tier voice transcription and email generation — hosted API, no local inference

`packages/ai/lib/sarvam.ts` calls the hosted Sarvam API (speech-to-text and
chat completion) entirely via HTTP `fetch`. There is no in-process model
inference, no native addon, and no local build/subprocess path involved —
the entire attack surface here is an outbound HTTPS request, which carries
no OS command injection risk.

### Operator CLI scripts — no shell-out, not internet-reachable regardless

`tooling/scripts/src/create-user.ts` and
`tooling/scripts/src/encrypt-existing-oauth-tokens.ts` — the only scripts in
this directory — are pure Node/Prisma database operations. Neither imports
`child_process` or any subprocess mechanism, and both are operator-run
locally (not reachable from any request path) regardless.

### On the listed deliverable (DAST scan)

As with the preceding 5.1.x controls, the checklist's deliverable text calls
for an external dynamic scan, tracked as the same open item under
[`3.1.1`](./3.1.1-urls-no-auth-material.md). Since this application never
executes an OS command from any request-reachable code path, a DAST scan
probing for OS command injection has no surface to exercise here.
