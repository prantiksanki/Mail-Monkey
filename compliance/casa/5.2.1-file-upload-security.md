# CASA 5.2.1 — Data Validation and Sanitization: Secure file upload handling

> **Control 5.2.1 — Data Validation and Sanitization / Securely handle untrusted
> files**
>
> *Protect against malicious file uploads by limiting uploads to expected file
> types and preventing direct execution of uploaded content.*
>
> **Deliverable**
> 1. Identify any situations in which the application accepts user file uploads.
>    Describe how the application securely validates file type and prevents file
>    execution. Provide detailed evidence such as source code, screenshots, or
>    other relevant sources.

---

## Short answer (for the CASA portal)

The application has exactly one file-upload feature — the "My Page" public
profile photo. A code review found that the upload's `Content-Type` was
entirely client-supplied and unenforced by the storage layer, meaning an
attacker could have stored a file with a browser-executable `Content-Type`
(e.g. `text/html`, `image/svg+xml`). This has been fixed by forcing a safe,
fixed `Content-Type` and `Content-Disposition` on every read of that bucket,
regardless of what was actually stored — closing the execution risk without
requiring the upload path to validate file content itself. Uploaded content is
served exclusively from a separate storage origin, not the application's own
origin, which already limited the impact to content-spoofing rather than
session/cookie compromise even before this fix.

---

## Deliverable — the one upload feature, the gap, and the fix

### The feature

`apps/web/modules/saas/settings/components/MyPageEditor/ProfileBlock.tsx` —
the public "My Page" profile photo. A file picker
(`<input type="file" accept="image/*">`) triggers a direct-to-storage upload:
the client requests a short-lived signed upload URL from the server
(`createProfilePhotoUploadUrl` → `packages/storage`'s `getSignedUploadUrl`),
then `PUT`s the selected file straight to Azure Blob Storage. This is the
**only** file-upload entry point anywhere in the application — confirmed by a
repo-wide search for `<input type="file">`, `FormData`, `req.formData()`, and
any oRPC procedure accepting a file/blob field.

### The gap found

The client sets `Content-Type: file.type` on the upload PUT
(`ProfileBlock.tsx`) — the browser-reported MIME type, which is fully
attacker-controlled (a script, or a renamed/relabeled file, can claim any
`Content-Type` regardless of actual content). `accept="image/*"` on the file
input is a UI hint only, not a security control.

The app's storage layer has two provider implementations, but only one is
live: `packages/storage/provider/index.ts` re-exports exclusively from
`./azure` — the S3 implementation exists in the codebase but is dead,
unreachable code.

Azure Blob Storage SAS tokens (the mechanism used for both the upload and
download URLs here) have **no way to constrain or validate the `Content-Type`
of an upload**. This differs from AWS S3's SigV4 presigned URLs, where a
signed header must match on the client's actual request or the signature is
rejected — Azure's SAS signature does not cover the `Content-Type` header at
all. Whatever `Content-Type` the client's PUT sends is simply stored as the
blob's property, unchecked.

**Concrete risk before the fix:** an authenticated attacker uploads a file to
their own profile-photo slot with `Content-Type: text/html` (embedding
`<script>`) or `image/svg+xml` (SVG can also embed `<script>`), and it would
be served back with that same browser-executable `Content-Type` when fetched.

**Mitigating factor, already true before this fix:** the only path that reads
this content, `apps/web/app/image-proxy/[...path]/route.ts`, issues a
client-side `NextResponse.redirect()` to the signed URL rather than proxying
bytes through the app server. So any malicious content, if ever rendered,
executes on the Azure Blob Storage origin (`https://<account>.blob.core.windows.net`)
— a different origin from the application (`popsuites.ai` /
`*.azurewebsites.net`). This ruled out session-cookie theft or same-origin
DOM access against the app even before the fix; the residual risk was
content-spoofing/phishing pages served from a URL that superficially looks
storage-account-hosted, and reflected-content abuse against anyone who opened
the direct URL.

### The fix

`packages/storage/provider/azure/index.ts`'s `getSignedUrl` (the read/download
path) now pins two **response-header overrides** on every generated SAS URL:

```ts
return buildSasUrl(path, bucket, permissions, expiresIn ?? 60 * 60, {
  contentType: "image/jpeg",
  contentDisposition: "inline",
});
```

`BlobSASSignatureValues.contentType`/`contentDisposition` (Azure's `rsct`/
`rscd` SAS query parameters) override the `Content-Type`/`Content-Disposition`
headers Azure serves on any GET/HEAD through that specific SAS URL —
**independent of what property is actually stored on the blob**. This is the
correct Azure-native mitigation for "the upload Content-Type can't be
trusted": rather than trying to validate or constrain the upload (which Azure
SAS doesn't support), every read this app issues is forced to declare a safe,
fixed type. Even if a blob were stored with `Content-Type: text/html`, a
request through this app's signed URL now always receives
`Content-Type: image/jpeg`, which no browser will parse/execute as HTML or
script.

**Verified in this session**: generated a signed URL with dummy Azure
credentials (SAS signing is a local HMAC operation — no live Azure account
needed to verify the query-string construction) and confirmed the resulting
URL's query string contains `rsct=image%2Fjpeg` and `rscd=inline`.

A client-side file-size guard (5 MB) was also added at
`ProfileBlock.tsx`'s `onPickPhoto`, documented explicitly as a UX/abuse-
reduction measure rather than a security boundary — Azure SAS has no native
mechanism to cap upload size, and a scripted request could bypass a
client-side check regardless. The actual execution/XSS risk this control is
about is fully closed by the Content-Type fix above, independent of file
size.

### Residual risk and future hardening (documented, not silently dropped)

- This fix protects every read that goes through this app's own
  `getSignedUrl()`/image-proxy path — the only read path that exists today.
  It would not protect a hypothetical future feature that reads blobs by some
  other mechanism (e.g. a public/anonymous container read, which this app
  does not use).
- A stronger, heavier alternative — inspecting actual file bytes at upload
  time via an Azure Event Grid `BlobCreated` trigger and correcting/quarantining
  mismatched content — was considered and intentionally not built now, given
  this app's single, narrow upload use case (always intended to be a profile
  photo). Recommended as a future hardening item if file-upload surface area
  grows (e.g. a feature accepting arbitrary user-supplied attachments).
