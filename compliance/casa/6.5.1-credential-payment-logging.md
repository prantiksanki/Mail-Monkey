# CASA 6.5.1 — Configuration: No credential/payment logging

> **Control 6.5.1 — Configuration / Do not log credentials or payment
> details**
>
> *The application shall not log credentials or payment details. Session
> tokens shall only be stored in logs in an irreversible, hashed form.*
>
> **Deliverable**
> 1. Provide a written description highlighting the protections to prevent
>    logging of credentials or payment details.
> 2. Provide a sample from a log captured during a login process.
> 3. Provide a sample from a log captured during a payment process (if
>    applicable).

---

## Short answer (for the CASA portal)

A code review found the most severe finding of this entire compliance
review: an error-logging hook in the authentication library configuration
was logging an internal context object that — confirmed directly against the
installed library's type definitions — carries the raw `BETTER_AUTH_SECRET`
signing secret, the live database adapter, and full session/user objects.
This has been fixed to log only the error itself. Four related, lower-severity
findings (OAuth account objects, a leftover debug log dumping unverified
webhook content, an unfiltered payment-provider error dump, and two generic
error handlers) have also been fixed. No raw session token is logged
anywhere in the codebase.

## Deliverable — findings and fixes

### 1. Fixed — the most severe finding: `packages/auth/auth.ts`, `onAPIError`

**Before:**
```ts
onAPIError: {
	onError(error, ctx) {
		logger.error(error, { ctx });
	},
},
```

Investigation initially suspected `ctx` here was the per-request endpoint
context (which would carry `ctx.body` — for `/sign-in/email`, a plaintext
`{ email, password }`). Deeper verification against the actual installed
type definitions (`@better-auth/core`'s `AuthContext` type,
`node_modules/.pnpm/@better-auth+core@.../dist/types/context.d.mts`) found
something **more severe**: this `ctx` argument is typed as `AuthContext`,
which includes:

```ts
type AuthContext = PluginContext & InfoContext & {
  // ...
  session: { session: Session & Record<string, any>; user: User & Record<string, any> } | null;
  secret: string;                    // ← BETTER_AUTH_SECRET itself
  adapter: DBAdapter<Options>;        // ← live database adapter
  internalAdapter: InternalAdapter<Options>;
  password: { hash: ...; verify: ...; };
  // ...
};
```

`logger.error(error, { ctx })` was logging this object wholesale on **every
API error** — including the application's master authentication signing
secret, a live database adapter reference, and full session/user data,
regardless of what triggered the error. This is a strictly worse finding
than the originally-suspected "logs the failed sign-in password" scenario,
though that risk isn't present either way: the `onError` callback's `ctx`
parameter is confirmed to be the auth-system context, not a per-request
context carrying the submitted request body.

**After:**
```ts
onAPIError: {
	onError(error) {
		// Never log the AuthContext argument — it carries `secret`
		// (BETTER_AUTH_SECRET itself), the live database adapter, and
		// full session/user objects. Only the error itself is safe to
		// log; better-auth's own error types don't carry request bodies.
		logger.error(error);
	},
},
```
`error` is typed `unknown` by better-auth (the thrown `APIError`/error
instance); logging just the error carries its message/status, which is the
normal, safe operational-error-logging pattern used everywhere else in this
codebase.

### 2. Fixed — OAuth account/payload objects logged wholesale: `packages/auth/auth.ts`

Two sites logged the full `account` (and `payload`) objects during Google
OAuth account creation:

```ts
// Before
logger.error("Google account creation attempted without valid idToken", { account });
// ...
logger.error("Google profile missing valid email field", { payload, account });
```

`account.accessToken`/`refreshToken`/`idToken` are AES-256-GCM-encrypted at
rest (see [`4.1.3`](./4.1.3-cryptographic-operations.md)), so these calls
were logging ciphertext rather than plaintext secrets — a materially lower
severity than the finding above — but still an unnecessary wholesale object
dump, inconsistent with the careful field-picking style already used
elsewhere in the same file. Fixed to log only non-sensitive identifiers:

```ts
// After
logger.error("Google account creation attempted without valid idToken", {
	userId: account.userId,
	providerId: account.providerId,
});
// ...
logger.error("Google profile missing valid email field", {
	sub: payload.sub,
	userId: account.userId,
});
```

### 3. Fixed — leftover debug logging of unverified webhook content: `packages/payments/provider/lemonsqueezy/index.ts`

```ts
// Before (removed entirely)
// TEMP DEBUG: confirm the webhook is reaching us and what it contains.
console.log("[ls-webhook] received", {
	hasSecret: !!process.env.LEMONSQUEEZY_WEBHOOK_SECRET,
	hasSignatureHeader: !!req.headers.get("x-signature"),
	bodyPreview: text.slice(0, 500),
});
```

Explicitly labeled leftover debug code (also relevant to
[`6.2.1`](./6.2.1-debug-mode.md)), logging the first 500 characters of the
webhook body **before signature verification runs** — LemonSqueezy
subscription/order webhooks carry customer email and billing name/address.
Removed entirely; the existing `"[ls-webhook] verified"` log after
successful signature validation already provides legitimate operational
visibility with only safe, specific fields (event name, subscription ID,
status).

### 4. Fixed — unfiltered payment-provider error response: `packages/payments/provider/creem/index.ts`

```ts
// Before
if (!response.ok) {
	logger.error("Failed to create checkout link", await response.json());
	throw new Error("Failed to create checkout link");
}
```

Logged the entire raw Creem API error-response body. Creem, like Stripe,
never returns raw card data to the merchant on a checkout-creation error —
so this was not a card-data leak — but the unfiltered response could echo
customer email/metadata, and didn't match the safer, message-only pattern
already used by Stripe and Polar in the same package. Fixed:

```ts
// After
if (!response.ok) {
	const errorBody = await response
		.json()
		.catch(() => null as { message?: string; error?: string } | null);
	logger.error("Failed to create checkout link", {
		status: response.status,
		message: errorBody?.message ?? errorBody?.error,
	});
	throw new Error("Failed to create checkout link");
}
```

### 5. Fixed — generic error objects logged wholesale: `packages/api/orpc/handler.ts`

Both `rpcHandler` and `openApiHandler`'s `onError` interceptors logged the
raw error object:
```ts
// Before
onError((error) => {
	logger.error(error);
}),
```
A thrown `ORPCError` can carry an arbitrary `.data` payload (confirmed
against `@orpc/client`'s `ORPCError` class — `this.data = options.data`), and
no procedure in this codebase currently attaches sensitive data to that
field, but nothing structurally prevents a future one from doing so. Fixed
defensively to log only the message:
```ts
// After
onError((error) => {
	// Log only the message, never the error object wholesale — a
	// thrown ORPCError can carry an arbitrary `.data` payload, and
	// validation errors can echo submitted field values.
	logger.error(
		error instanceof Error ? error.message : String(error),
	);
}),
```

### Already reviewed, not a gap: the operator CLI password display

`tooling/scripts/src/create-user.ts` prints a system-generated initial
password to the console once, for the operator running the script — this is
a one-time CLI display to the person who just ran the command, not a
persistent log file or log aggregator. Already documented as an accepted
exception under [`1.1.2`](./1.1.2-authentication.md), where the account is
also gated to require a forced password change on first login.

### Confirmed clean: no raw session-token logging, no Prisma query logging

- No occurrence anywhere in the codebase logs a raw session token or cookie
  value.
- `packages/database/prisma/client.ts` does not enable Prisma's query
  logging (`log: ["query"]`), so bound parameter values (which could include
  tokens or password hashes passed to a query) are never written to logs via
  that mechanism either.

### Sample log output (original, code-review-derived)

**Login process (failed sign-in attempt, after the fix):**
```
ERROR  [APIError: Invalid email or password]
```
No request body, email, or password is present in the log line.

**Payment process (failed checkout-link creation, after the fix):**
```
ERROR  Failed to create checkout link { status: 400, message: "Invalid product_id" }
```
No card data, customer PII beyond what's already in the operator's own
dashboard, or raw API response is present.

## Re-verification with a live-captured sample — 2026-09-12

The sample above was derived from code review, not an actual captured log line.
To produce a genuine deliverable, one deliberately-invalid sign-in request was sent
to `https://staging.popsuites.ai/api/auth/sign-in/email` (a nonsense
`casa-log-sample-test@example.invalid` address, no real account, well under the
5-attempt lockout threshold), while tailing the live container log stream
(`az webapp log tail --name zer0email-staging-web --resource-group
zer0email-staging-app` — this reads Linux App Service's container stdout directly;
`applicationLogs.fileSystem` is currently `Off` in the App Service config, which
doesn't block this).

**Actual captured log lines:**
```
2026-09-12T12:14:23.248Z <-- POST /api/auth/sign-in/email
2026-09-12T12:14:24.220Z ERROR [Better Auth]: User not found { email: 'casa-log-sample-test@example.invalid' }
2026-09-12T12:14:24.231Z --> POST /api/auth/sign-in/email 401 984ms
```

**This does not match the sample above.** The `ERROR [APIError: Invalid email or
password]` line (from this app's own `onAPIError` hook, logged via `@repo/logs`'s
consola — no timestamp, that formatting) never appeared in the live capture. What
fired instead is **better-auth's own internal logger** (default format, carries a
timestamp) logging a `"User not found"` message with the attempted email address.
`packages/auth/auth.ts`'s `betterAuth({...})` config does not currently pass a
`logger` option to override this.

**Assessment:** still no password, session token, or payment detail present — the
control's actual prohibited items are absent, so this is compliant with 6.5.1 as
written (an attempted email address is a user identifier, not a "credential" or
"payment detail"). But it's a real, previously-undocumented behavior difference:
the fix verified in the section above (`onAPIError`) is still correctly in place,
it simply isn't the log line that fires on this particular error path — better-auth's
own internal logging was never in scope of that earlier review. Flagged here rather
than silently left as-is; if stricter (no-email-in-logs) behavior is wanted, this
would require configuring or wrapping better-auth's internal logger.
