# CASA 1.3.2 — Authentication: Out‑of‑band verifiers used exactly once

> **Control 1.3.2 — Authentication / Out of band verifiers shall be random and not
> reused**
>
> *Out of band verifier shall only be used once.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the out of band expiration process.

---

## What this control adds beyond 1.3.1

`compliance/casa/1.3.1-oob-verifiers.md` confirms each verifier is random and expires
within a reasonable window. This control is stricter: a verifier must not be
successfully redeemable **twice**, including under a race — two requests submitting
the same still‑valid verifier at nearly the same instant. That requires the
"is this still valid" check and the "mark it used" write to be a single atomic
operation, not two separate steps.

---

## Short answer (for the CASA portal)

External identity providers (**Google**, **Microsoft** OAuth 2.0) issue and consume
their own OOB verifiers. Of the application's four proprietary OOB verifiers, the two
issued by this repo's own code — the Telegram bot login OTP and the Telegram
account‑link token — are consumed via an **atomic claim‑with‑guard** (a single
`updateMany`/`deleteMany` scoped to the still‑unused row, gated on the affected‑row
count), so a concurrent replay of the same verifier cannot succeed twice. The
remaining two — Better Auth's email‑verification link and password‑reset token — have
a narrow, low‑severity timing window in the library's compiled route handlers; see
Deliverable 2 for the accepted‑risk assessment.

## Deliverable 2 — Single-use enforcement per verifier

| OOB verifier | Consume mechanism | Race-safe? |
|---|---|---|
| **Telegram login OTP** | `handleOtpInput` → `consumeLoginState` (`packages/api/modules/telegram/service.ts`): after the code comparison passes, deletes the `Verification` row scoped to **both** the `identifier` **and** the exact serialized `state` just read (`db.verification.deleteMany({ where: { identifier, value: JSON.stringify(state) } })`), then checks `result.count === 1` before proceeding. A concurrent second submission reading the same row will find it already gone and its delete matches zero rows. | **Yes** (fixed in this change — see below) |
| **Telegram account‑link token** | `consumeTelegramLinkToken` (`packages/database/prisma/queries/telegram.ts`): after an initial fetch for validity/messaging, atomically claims via `updateMany({ where: { id, usedAt: null, expiresAt: { gt: new Date() } }, data: { usedAt: new Date() } })` and checks `result.count !== 1`, mirroring the existing `claimTelegramAction` pattern in the same file. | **Yes** (fixed in this change — see below) |
| **Email verification link** | Better Auth `verifyEmail` (`node_modules/better-auth/dist/api/routes/email-verification.mjs`): reads `user.user.emailVerified`, and if `false`, unconditionally calls `internalAdapter.updateUserByEmail(email, { emailVerified: true })`. No atomic `UPDATE ... WHERE emailVerified = false` guard. | **No — accepted risk, see below** |
| **Password‑reset token** | Better Auth `resetPassword` (`node_modules/better-auth/dist/api/routes/reset-password.mjs`): reads/validates the verification row, updates the password, and only afterward calls `deleteVerificationValue`. No single atomic operation ties validation, the password write, and the deletion together. | **No — accepted risk, see below** |

### Fixes applied in this repo (Telegram verifiers)

Both Telegram consume paths previously did a plain **read‑then‑write**: fetch the row,
check it's still valid, then separately mark it used. Two requests racing on the same
verifier could both pass the read before either write landed. Both are now an
**atomic claim**: the "mark used" write is scoped, in its own `WHERE` clause, to the
row still being unused (`usedAt: null` for the link token; the exact still‑matching
`value` for the OTP state), and the caller checks the affected‑row count before
treating the verifier as consumed. A losing concurrent request gets `count === 0` /
`!== 1` and is told the verifier was already used, exactly as if it had submitted a
stale one.

### Accepted risk: Better Auth's email-verification and password-reset routes

Both routes are compiled library internals
(`node_modules/better-auth/dist/api/routes/*.mjs`) invoked directly by Better Auth's
router; `packages/auth/auth.ts` configures `emailVerification` /
`emailAndPassword` *options* (templates, expiry, hooks) but does not — and, absent a
custom endpoint override, cannot cleanly — replace this internal
check‑then‑write sequence with an atomic one. Forking or `patch-package`-ing the
library was considered and rejected: patches are silently dropped on a clean
`node_modules` reinstall unless independently re‑applied and maintained, and are
liable to silently break (or silently stop applying) on every `better-auth` version
bump, trading a narrow, already‑low‑severity timing bug for an ongoing maintenance
liability.

**Severity assessment:** low.
- Exploitation requires the attacker to already possess a valid, non‑expired verifier
  for the target account — this is not a way to guess or brute‑force a verifier, only
  to double‑spend a legitimately obtained one within a very small window (a single DB
  round‑trip, typically single‑digit milliseconds).
- The practical worst case is idempotent or low‑impact: for email verification, at
  most two requests both flip the same boolean and each independently call
  `onEmailVerification`/`autoSignInAfterVerification` (i.e. up to two sessions
  created, not account takeover of a different account). For password reset, at most
  two requests both successfully set the password to the same or different new
  values in quick succession — the end state is still a normal password change, not a
  bypass of any check.
- There is no cross‑account or privilege‑escalation impact: the race only lets the
  legitimate holder of a verifier "use" it more than once against their own account.

**Mitigation in place:** none beyond the library's own expiry and single‑use *intent*
(the flag/row‑deletion still happens — it merely isn't atomic with the check).

**Recommendation:** re‑verify this control whenever `better-auth` is upgraded, in
case upstream tightens these handlers to an atomic conditional update; if the gap
becomes a practical concern (e.g. is escalated by a client's security policy or an
external pentest), consider a purpose‑built override endpoint for `/verify-email` and
`/reset-password` that reimplements the check‑and‑set atomically ahead of delegating
to Better Auth, rather than patching the library in place.
