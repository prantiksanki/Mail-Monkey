# CASA 6.2.1 — Configuration: Disable debug modes in production

> **Control 6.2.1 — Configuration / Disable debug modes in production
> environments**
>
> *Disable debug modes in production environments.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

A code review found one genuine debug-information leak: an authenticated-user
diagnostics endpoint unconditionally returned a raw `error.stack` trace in its
API response, with no production gate. This has been fixed. Every other
debug-mode surface checked — Next.js build/runtime mode, `better-auth`
verbosity, `NODE_ENV` handling, and the presence of any dev-only route — was
already correctly configured for production.

---

## Deliverable — the gap, the fix, and everything already protected

### Gap found and fixed: stack trace leak in mailbox diagnostics

`packages/api/modules/mailboxes/procedures/diagnose-mailbox-extended.ts`
(`protectedProcedure`, ownership-checked — only the mailbox's own owner can
call it) unconditionally included a raw stack trace in its response:

```ts
} catch (error) {
  diagnostics.error = error instanceof Error ? error.message : String(error);
  diagnostics.stack = error instanceof Error ? error.stack : undefined;
  return diagnostics;
}
```

This is not a cross-user leak — the endpoint is scoped to the caller's own
mailbox — but it unconditionally served internal stack traces (file paths,
call structure, library internals) to any authenticated user in production,
with no `NODE_ENV` gate. This is the textbook shape of "debug mode left on in
production": diagnostic detail meant for local development, shipped
unconditionally to a live API response.

**Fix:**

```ts
} catch (error) {
  diagnostics.error = error instanceof Error ? error.message : String(error);
  // Stack traces leak internal file paths/library internals — only
  // useful for local debugging, never to a production API response.
  if (process.env.NODE_ENV !== "production") {
    diagnostics.stack = error instanceof Error ? error.stack : undefined;
  }
  return diagnostics;
}
```

`diagnostics.error` (the short error message) is retained unconditionally —
that's normal, useful self-service diagnostic information for a user
troubleshooting their own mailbox connection, not an information-disclosure
issue. Only the raw stack trace, the part with no legitimate production use,
is now gated.

### Already protected — checked and confirmed

- **Runtime mode:** `apps/web/package.json`'s `build`/`start` scripts run
  `next build` then `next start` (or the deployed `.next/standalone` output's
  equivalent) — `next dev` is never invoked in `.github/workflows/deploy-prod.yml`.
- **`NODE_ENV`:** standard Next.js-managed — `next build`/`next start` set it
  to `production` automatically, and `packages/api/lib/rate-limit.ts` already
  relies on this correctly (`process.env.NODE_ENV !== "production"` gates its
  dev-mode rate-limit bypass) — the same pattern now used for the fix above.
- **Next.js config** (`apps/web/next.config.ts`): no `reactStrictMode` debug
  override; `productionBrowserSourceMaps` is not set (defaults to `false` —
  no client-side source maps shipped to production); `poweredByHeader: false`.
- **`better-auth`** (`packages/auth/auth.ts`): no `debug`/`verbose` option is
  set on `betterAuth()`.
- **No debug routes:** no `/debug`, `/_debug`, `/api/debug`, or
  `DEBUG_MODE`/`SHOW_DEBUG`-style environment-gated route exists anywhere in
  `apps/web` or `packages/api`.

### Reviewed, not changed

- **`/docs` OpenAPI reference route** (`packages/api/orpc/handler.ts`) exposes
  the API's route/schema documentation (a Swagger-UI-style reference), not
  server internals, secrets, or stack traces. Since this is a public-facing
  SPA, the same route/schema surface is already discoverable from the client
  bundle — this isn't treated as a debug-mode gap, just standard API
  documentation.
- **`diagnose-mailbox.ts`** (the sibling procedure without a `.stack` field)
  returns internal database IDs, OAuth scopes, and token-presence booleans —
  but only for the caller's own mailbox/account, which is reasonable
  self-service diagnostic detail, not the specific "debug mode" failure this
  control targets. Left unchanged.
- **`packages/logs/lib/logger.ts`** has no log-level gating tied to
  `NODE_ENV` — the same console verbosity applies in development and
  production. This is server-side operational logging (stdout/stderr), not
  information disclosed to a client response, so it's a distinct (ops-hygiene)
  concern from what 6.2.1 targets. Noted as a minor follow-up, not fixed in
  this pass.

### On the listed deliverable (DAST scan)

As with the 5.1.x/5.2.1 controls, the checklist's deliverable text calls for
an external dynamic scan, tracked as the same open item under
[`3.1.1`](./3.1.1-urls-no-auth-material.md). This write-up documents the fix
that should prevent a stack-trace-disclosure finding in such a scan.
