# CASA 1.3.3 — Authentication: Out‑of‑band verifiers securely random

> **Control 1.3.3 — Authentication / Out of band verifiers shall be random and not
> reused**
>
> *Out of band verifier shall be securely random.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the algorithm used to generate initial authentication
>    codes.

---

## Short answer (for the CASA portal)

Every out‑of‑band verifier the application generates — email verification links,
password‑reset links, magic links, and the Telegram‑bot login code — is produced by
a **cryptographically secure pseudo‑random number generator (CSPRNG)**: the Web
Crypto `crypto.getRandomValues()` (Better Auth) or Node.js `crypto.randomInt()` /
`crypto.randomBytes()` (Telegram integration), both seeded from the operating
system's entropy source. No use of `Math.random()` or any non‑cryptographic RNG
exists in any authentication, token, or OTP code path. Character/number selection
uses **rejection sampling** so the output is uniformly distributed with no modulo
bias.

## Deliverable 2 — Algorithm used to generate authentication codes (proprietary)

### A. Better Auth `1.4.7` — string tokens (magic link, password‑reset token, IDs)

Random strings come from `@better-auth/utils@0.3.0` →
`createRandomStringGenerator(...)`
(`node_modules/@better-auth/utils/dist/random.mjs`). Algorithm:

1. Build the target character set (e.g. `a‑z A‑Z` for magic links, `a‑z A‑Z 0‑9`
   for `generateId`).
2. Compute `maxValid = floor(256 / charSetLength) * charSetLength` — the largest
   multiple of the alphabet size that fits in one byte.
3. Fill a `Uint8Array` buffer by calling **`crypto.getRandomValues(buf)`** (the Web
   Crypto CSPRNG; in this Node runtime it is backed by OpenSSL `RAND_bytes` / the OS
   CSPRNG).
4. For each byte `b`: if `b < maxValid`, append `charSet[b % charSetLength]`;
   otherwise **discard the byte** (rejection sampling). Refill the buffer when
   exhausted. Repeat until the requested length is reached.

Rejection sampling in step 4 guarantees each character is uniformly distributed —
there is no modulo bias toward the start of the alphabet.

Applied as:
- **Magic‑link token** — `generateRandomString(32, "a-z", "A-Z")` → 52‑char
  alphabet, 32 chars ≈ **182 bits** of entropy
  (`node_modules/better-auth/dist/plugins/magic-link/index.mjs:54`).
- **Password‑reset token** — `generateId(24)` → 62‑char alphabet, 24 chars
  ≈ **143 bits**
  (`node_modules/better-auth/dist/api/routes/reset-password.mjs:62`; `generateId`
  defined in `@better-auth/core` → `utils`, same generator over `a‑z A‑Z 0‑9`).

### B. Better Auth — email verification link (signed token, not a random string)

The verification link carries an **HS256 JWT** created by `signJWT(...)`
(`node_modules/better-auth/dist/api/routes/email-verification.mjs:3`, `:13`),
signed with the server secret `BETTER_AUTH_SECRET`. Its unpredictability derives
from the HMAC‑SHA‑256 keyed with that high‑entropy secret rather than from a random
body; it cannot be forged or guessed without the secret. The JWT includes an `exp`
claim (1 hour).

### C. Better Auth — password salt (context: how the stored secret is randomised)

`hashPassword` draws the per‑password salt directly from the CSPRNG:
`crypto.getRandomValues(new Uint8Array(16))` — 128 bits
(`node_modules/better-auth/dist/crypto/password.mjs`).

### D. Telegram bot integration — login OTP and account‑link token

Uses Node's `node:crypto` module (OpenSSL CSPRNG):

- **Login OTP** — `String(randomInt(100000, 1000000))`
  (`packages/api/modules/telegram/service.ts:1`, `:367‑368`). `crypto.randomInt`
  returns a uniformly distributed integer in `[min, max)` using rejection sampling
  internally; here that is a 6‑digit code (900 000 possible values), rate‑limited to
  3 attempts and expiring in 10 minutes.
- **Account‑link token** — `randomBytes(24).toString("base64url")`
  (`packages/database/prisma/queries/telegram.ts:1`, `:7`) → **192 bits** of
  CSPRNG output, expiring in 15 minutes.

### E. Negative confirmation

Repository search for `Math.random` across `packages/auth`,
`packages/api/modules/telegram`, `packages/database/prisma/queries`, and
`apps/web/modules/saas/auth`: **no matches**. No custom or weak RNG, no
timestamp‑ or counter‑derived codes, no predictable seeds.

### Summary against the control

All initial authentication codes / verifiers are generated by a CSPRNG
(`crypto.getRandomValues` or `node:crypto`), sampled without bias, with 143–192 bits
of entropy for string tokens and a 900 000‑value space for the 6‑digit OTP (bounded
further by attempt limits and short expiry). This meets "securely random".
