# CASA 4.1.4 — Communications: Cryptographic modules fail securely

> **Control 4.1.4 — Communications / Protect confidential data through strong
> cryptography**
>
> *All cryptographic modules shall fail securely, and errors are handled in a way
> that does not enable Padding Oracle attacks.*
>
> **Deliverable**
> 1. Describe how your application handles cryptographic failures for the
>    previously identified crypto operations. Provide detailed evidence such as
>    source code, screenshots, or other relevant sources that showcase how the
>    application handles cryptographic failures.

---

## Short answer (for the CASA portal)

No CBC-mode cipher is used anywhere in this application's own code, so the classic
padding-oracle attack surface (a decryption error that distinguishes "bad padding"
from "bad MAC" on a byte-by-byte basis) does not exist here. Every cryptographic
verification/decryption operation in the app either uses an authenticated mode
(AES-256-GCM for the new OAuth-token encryption) that rejects tampered ciphertext
with a single generic error before any plaintext is returned, or a constant-time
comparison (HMAC/MAC checks, now fixed everywhere — see below) that reveals no
timing signal about *how much* of a guess was correct.

## Deliverable — failure handling per operation

### Password hashing (scrypt) — already secure

Verification failure (`verifyPassword`) is a boolean `false`, computed via
constant-time comparison — see [`1.1.3`](./1.1.3-password-storage.md). No partial
information about the correct password is ever leaked through timing or error
content.

### OOB verifier validation (JWT, tokens, OTP) — already secure

Each verifier type rejects on expiry/mismatch with a generic "invalid or expired"
outcome — see [`1.3.1`](./1.3.1-oob-verifiers.md) and
[`1.3.2`](./1.3.2-oob-single-use.md) for the single-use/race-safety angle, which is
the adjacent failure-mode concern for this same set of operations.

### Google idToken JWT verification (RS256) — already secure

`jwtVerify` (from `jose`, `packages/auth/auth.ts`) throws a single error on any
failure — expired, wrong issuer/audience, bad signature, malformed token — and the
catch block logs and re-throws a generic `"Invalid or forged Google idToken"`
message without distinguishing which specific check failed to the caller. RS256
verification is itself not susceptible to padding-oracle attacks (it's a signature
scheme, not a padding-based encryption mode).

### OAuth token encryption (AES-256-GCM) — new, secure by construction

This is the operation most directly relevant to this control, since it's the one
symmetric-encryption operation in the app (added under
[`4.1.3`](./4.1.3-cryptographic-operations.md)) and the one where a naive
implementation could have introduced exactly the failure mode this control warns
against.

- **Why GCM avoids the padding-oracle class of bug:** GCM is an
  *authenticated* mode — it computes and checks a MAC (the auth tag) as part of
  decryption, before any plaintext is released to the caller. `decryptToken`
  (`packages/utils/lib/token-crypto.ts`) calls `decipher.setAuthTag(authTag)` then
  `decipher.final()`; `final()` throws (`"Unsupported state or unable to
  authenticate data"`, Node's built-in message) if the tag doesn't match the
  ciphertext — verified directly in this session: encrypting a token, corrupting a
  few bytes of the stored ciphertext, and calling `decryptToken` on it throws
  immediately rather than returning corrupted or partial plaintext.
- **No distinguishable failure modes:** unlike classic CBC+padding schemes (where
  "bad padding" and "bad MAC" can be timed or reported differently, letting an
  attacker binary-search the plaintext byte by byte), GCM has exactly one failure
  path — authentication failure — and Node's `crypto` module surfaces it as one
  generic exception. The caller (every read site listed in `4.1.3`) does not
  attempt to recover or interpret the error; it propagates as an unhandled
  exception, which is the correct "fail closed" behavior for a corrupted or
  tampered credential.
- **Malformed-input handling:** `decryptToken` also validates the stored format
  (`<iv>:<authTag>:<ciphertext>`, three colon-separated segments) before attempting
  decryption, throwing `"Invalid encrypted token format"` for anything else —
  so a corrupted or foreign value fails at parsing rather than being fed
  byte-by-byte into the cipher.

### Webhook HMAC signature verification — fixed as part of this review

Two comparisons were found using plain `!==`/`===` string inequality instead of a
constant-time comparison — a timing side-channel that, while not a padding-oracle
in the classical sense, is the same underlying class of bug this control is meant
to catch (an error/comparison path that leaks information an attacker can use to
forge a valid credential without knowing it outright).

| Location | Before | After |
|---|---|---|
| `packages/payments/provider/creem/index.ts` | `computedSignature !== signature` (plain string compare) | `Buffer` length pre-check + `timingSafeEqual` |
| `packages/api/modules/telegram/webhook.ts` | header `!== expectedSecret` (plain string compare) | `Buffer` length pre-check + `timingSafeEqual` |

Both now match the pattern already used correctly elsewhere in the codebase
(`packages/payments/provider/lemonsqueezy/index.ts`), which was the reference this
fix was modeled on. `timingSafeEqual` throws if the two buffers differ in length,
so both call sites check `.length` first and fail the request (HTTP 400/401)
rather than letting `timingSafeEqual` throw an uncaught exception.

Verified in this session: a small script confirmed the corrected comparison
accepts a correctly-signed payload, rejects an incorrectly-signed one, and rejects
a different-length signature — all without a length-dependent short-circuit.

### Not applicable

No CBC-mode cipher, no custom padding scheme, and no `crypto.subtle.decrypt` with
a non-authenticated mode exists anywhere in this codebase (confirmed by the
repo-wide audit under [`4.1.3`](./4.1.3-cryptographic-operations.md)). The only
CBC occurrence in the entire dependency tree is inside Better Auth's own library
code for an optional, unused JWE `cookieCache` strategy (`A256CBC-HS512`, which is
itself an authenticated Encrypt-then-MAC construction per RFC 7518 §5.2.5, not
susceptible to padding-oracle attacks even if it were enabled) — this app does not
set `strategy: "jwe"`, so that code path never executes.
