# CASA 6.6.1 — Session Management: Browser storage cleared on logout

> **Control 6.6.1 — Session Management / Securely clear client storage
> during logout**
>
> *Browser storage is securely cleared during logout.*
>
> **Deliverable**
> Provide a written description of what (if any) confidential data or
> authentication material is stored in the browser after user logout.

---

## Short answer (for the CASA portal)

No authentication material is ever stored in browser storage — the session
lives only in an httpOnly cookie, managed entirely by `better-auth`'s server,
and is invalidated server-side plus cleared via `Set-Cookie` on sign-out. A
code review found one piece of non-secret, account-linked application state
(the user's selected-mailbox id) persisted in `localStorage` and never
cleared on logout; this has been fixed by clearing it at every place a
session ends. After the fix, `localStorage` is confirmed empty of any
account-linked data post-logout.

---

## Deliverable — what's stored, and what's cleared

### Session/auth material: never in browser storage (no fix needed)

`better-auth` (`packages/auth/auth.ts`) is configured with
`useSecureCookies` and `session.cookieCache`; the session token and cached
session payload live only in an httpOnly, `Secure`, `SameSite` cookie set by
the server. The `better-auth` client (`packages/auth/client.ts`) registers
no storage persister — confirmed by reading its plugin list (magic-link,
org, admin, passkey, 2FA, generic-OAuth, username; none add client-side
storage). Calling `authClient.signOut()` triggers the server to invalidate
the session record and clear the cookie via `Set-Cookie`; there is no
parallel copy of the token or session in `localStorage`/`sessionStorage` for
JavaScript to fail to clean up.

TanStack Query (`apps/web/modules/shared/components/ApiClientProvider.tsx`)
is configured with no persister plugin — the query cache is in-memory only
and is discarded on the full-page navigation (`window.location.href = ...`)
that already follows every logout in this app.

### Fixed — `localStorage["zeromail.selectedMailboxId"]` not cleared on logout

`apps/web/modules/saas/mailboxes/lib/selected-mailbox-context.tsx` persists
which mailbox the user last had selected, under
`localStorage["zeromail.selectedMailboxId"]`, so the choice survives a page
reload. This value isn't a credential, but it is account-linked state, and
it was never removed when a session ended — on a shared browser profile, the
next person to sign in would see the previous user's mailbox selection
auto-restored until they picked a different one.

**Three places end a session and redirect**, all with this same gap:

- `apps/web/modules/saas/shared/components/UserMenu.tsx` — `onLogout`
  (sign-out from the user menu)
- `apps/web/modules/saas/shared/components/NavBar.tsx` — `onLogout`
  (sign-out from the mobile nav)
- `apps/web/modules/saas/settings/components/ActiveSessionsBlock.tsx` —
  `revokeSession`, specifically the branch where the session being revoked
  is the caller's own current session (functionally a logout)

**Fix:** added one shared helper,
`apps/web/modules/saas/shared/lib/clear-client-state.ts`:

```ts
import { SELECTED_MAILBOX_STORAGE_KEY } from "@saas/mailboxes/lib/selected-mailbox-context";

export function clearClientStateOnLogout() {
	if (typeof window === "undefined") {
		return;
	}
	localStorage.removeItem(SELECTED_MAILBOX_STORAGE_KEY);
}
```

and call it, right before the existing redirect, at all three sites, e.g.
(`UserMenu.tsx`):

```ts
const onLogout = () => {
	authClient.signOut({
		fetchOptions: {
			onSuccess: async () => {
				clearClientStateOnLogout();
				window.location.href = new URL(
					config.saas.redirectAfterLogout,
					window.location.origin,
				).toString();
			},
		},
	});
};
```

Centralizing this in one helper (rather than patching the removal into each
of the three call sites separately) means a future new place that ends a
session only has to call `clearClientStateOnLogout()`, not rediscover which
keys need clearing.

### Reviewed, not a gap: analytics

`apps/web/modules/analytics/provider/mixpanel/index.tsx` initializes
Mixpanel with `persistence: "localStorage"` — but this provider is dead
code. The app's active analytics provider is resolved through the `@analytics`
path alias, which is pinned to the **Google Analytics** provider
(`apps/web/modules/analytics/index.tsx:2` re-exports
`./provider/google`; `ClientProviders.tsx` imports `AnalyticsScript`/
`useAnalytics` only from that alias). Mixpanel's `AnalyticsScript` is never
rendered and `mixpanel.init()` never runs, so no Mixpanel data — identifying
or otherwise — is ever written to `localStorage` in the deployed app. (Also
separately confirmed: even if it were wired in, `mixpanel.identify()` is
called nowhere in the codebase, so no PII would be attached to its anonymous
distinct_id.) Google Analytics/GTM state (`_ga`/`dataLayer`) is anonymous
usage analytics, not authentication material or confidential user data, and
is out of scope for this control.

### Sample: `localStorage` contents after logout (post-fix)

```
> Object.keys(localStorage)
[]
```

(The theme preference, if a user has set one, is stored via `next-themes` in
`localStorage["theme"]` and intentionally survives logout — it's a
UI preference, not account or authentication data, and CASA 6.6.1 is scoped
to confidential/authentication material.)
