## What HTTP parameter pollution (HPP) is

A request supplies the same parameter name more than once (e.g. `?id=1&id=2`, or
duplicate form fields). HPP becomes exploitable when different layers of a stack —
a WAF/proxy, the app framework's router, and a downstream service — each resolve
the duplicate differently (first wins here, last wins there), letting an attacker
smuggle a value past one layer's validation while a later layer acts on the other
value.

---

## Short answer (for the CASA portal)

This application has a single, consistent request-parsing path with no
proxy/WAF layer in front of it to disagree with the app: every query parameter
flows through oRPC's bracket-notation deserializer, which turns a duplicated key
into an array rather than silently picking a winner, and that array is then
rejected outright by Zod's scalar-typed schemas (required by this codebase's own
API conventions) before it ever reaches application logic. There is no second
query-parsing path anywhere in the app to produce a conflicting interpretation.

---

## Deliverable — architecture and evidence

### Single parsing path, no dual-parser precondition

HPP requires at least two components that each parse the same request and can
disagree. This app has exactly one:

```
Request (Fetch-standard) → Hono's handle() adapter → oRPC's OpenAPIHandler
```

- `apps/web/app/api/[[...rest]]/route.ts` mounts the Hono app via `hono/vercel`'s
  `handle()` and delegates everything to `packages/api/orpc/handler.ts`.
- No route handler in `packages/api` calls `c.req.query()` directly (repo-wide
  search: zero matches) — there is no second, bespoke query-parsing path that
  could interpret a duplicate key differently from oRPC's own parser.
- No CDN, WAF, or reverse proxy sits in front of the app (confirmed under
  [`4.1.1`](./4.1.1-tls-configuration.md) — Azure App Service direct), so there is
  no edge layer with its own parameter-resolution rules to diverge from the app.

### Duplicate keys become arrays, not a silently-resolved scalar

oRPC's `StandardBracketNotationSerializer.deserialize()`
(`@orpc/openapi-client/dist/shared/openapi-client.t9fCAe3x.mjs`) is the actual
query-string deserializer, fed from `request.url.searchParams`. Read directly in
this session:

```js
} else if (nextSegment in currentRef) {
  if (Array.isArray(currentRef[nextSegment])) {
    currentRef[nextSegment].push(value);
  } else {
    currentRef[nextSegment] = [currentRef[nextSegment], value];
  }
}
```

A repeated key (`?id=1&id=2`) does not resolve to "1" or "2" — it resolves to
`["1", "2"]`. There is no first-wins/last-wins behavior to exploit at this layer.

### The array is then rejected, not coerced into a scalar

That array next passes through oRPC's `SmartCoercionPlugin`
(`@orpc/json-schema/dist/index.mjs`), which attempts to coerce the raw input to
match each field's Zod schema. For a string-typed field:

```js
case "string": {
  if (typeof coerced !== "string") {
    satisfied = false;
  }
  break;
}
```

An array value fails this check (`satisfied = false`), and coercion fails —
`z.string()`/`z.coerce.number()`/every scalar Zod schema this codebase uses per
`.claude/rules/api-conventions.md` ("Validate all inputs with Zod schemas") then
rejects the request with a validation error. The duplicate-parameter request never
reaches a procedure handler with an ambiguously-resolved value; it is refused
before application logic runs at all.

### Security-relevant query params — consistently single-valued

The one query parameter used for a security-relevant decision is `redirectTo` (the
post-login redirect target): built in `apps/web/proxy.ts` and read via
`URLSearchParams.get()` / React Router's `useSearchParams().get()` in
`LoginForm.tsx`, `OtpForm.tsx`, and `SignupForm.tsx` — all first-value-only, and
consistent between however the value was produced and how it's consumed. No place
in the app reads this parameter with `getAll()` or otherwise treats it as
potentially multi-valued.

### Body parsing — not an HPP vector here

No `req.formData()` or manual `URLSearchParams`-on-body parsing exists anywhere in
`apps/web`/`packages/api`. The only `req.text()` usage is payment-webhook
signature verification (Stripe, Creem, LemonSqueezy, DodoPayments, Polar —
`packages/payments/provider/*/index.ts`), which reads the raw body for HMAC
verification and then JSON-parses it — JSON has no duplicate-key ambiguity
comparable to form/query parameter pollution (a duplicate JSON key is a
well-defined last-value-wins per `JSON.parse`, applied consistently by the single
JS runtime parsing it).

### On the listed deliverable (DAST scan)

The checklist's deliverable text calls for a dynamic scan (ADA's DAST guidance).
That is an external, tooling-driven exercise outside what a code review can
produce directly — flagged here as the same open item already tracked under
