# CASA 6.7.1 — Configuration: Securely store server-side secrets

> **Control 6.7.1 — Configuration / Securely store server-side secrets**
>
> *The application shall securely store access tokens, API keys, and other
> server-side secrets.*
>
> **Deliverable**
> Provide a written description along with relevant evidence (source code,
> screenshots, architecture diagrams, etc.) describing your approach to
> secrets management for any access tokens, API keys, or other server-side
> secrets used by the application.

---

## Short answer (for the CASA portal)

Server-side secrets never enter version control: `.env*` files are
gitignored (only a placeholder-only `.env.local.example` is tracked), every
CI/CD workflow injects secrets exclusively from GitHub Actions' encrypted
secrets store, and both deploy workflows run a `gitleaks` scan as a hard gate
before build/deploy. At runtime, secrets are held as environment variables
by Azure App Service. A codebase-wide search found no hardcoded
secret-shaped literal anywhere in source. One unrelated finding — a
Terraform state file for a separate AWS sidecar, committed to git — is noted
below as out of this control's scope but worth a decision.

---

## Deliverable — secrets flow, source to runtime

### 1. Source control: secrets are gitignored, only a placeholder file is tracked

`.gitignore` excludes every real env file:

```
.env
.env.local
.env.development.local
.env.test.local
.env.production.local
.env*.bak*
```

`git ls-files | grep -i '\.env'` returns only `.env.local.example` — a
template with placeholder values (`your-secret-here`-style strings), used to
document which variables a developer needs to set locally. No real secret
value has ever been committed under an `.env*` filename.

A repo-wide pattern search for common secret shapes (Stripe live/test keys
`sk_live_`/`sk_test_`, AWS access key IDs `AKIA...`) returned zero matches in
application source, confirming no hardcoded secret literal exists in the
codebase today.

### 2. CI/CD: secrets come only from GitHub Actions' encrypted store

`.github/workflows/deploy-staging.yml` and `deploy-prod.yml` reference
`${{ secrets.* }}` (77 occurrences combined across the four workflow files)
to inject API keys, database URLs, and signing secrets as job-step
environment variables at build/deploy time — never written to a file in the
repo or the built image layer history. These are GitHub's own
encrypted-at-rest, access-controlled repository/environment secrets; nothing
in this codebase re-implements secret storage for CI.

### 3. CI gate: `gitleaks` scans every push before deploy

`deploy-staging.yml`, `deploy-prod.yml`, and `validate-prs.yml` all run a
`gitleaks` secret-scanning job. A pull request or push that introduces a
credential-shaped string into tracked source is caught before it can reach a
deployed environment, independent of the `.gitignore`/code-review path.

### 4. Runtime: environment variables held by the hosting platform

The built app reads secrets via `process.env.*` (e.g.
`packages/payments/provider/creem/index.ts:19`,
`packages/payments/provider/lemonsqueezy/index.ts:27`,
`packages/auth/auth.ts`'s `BETTER_AUTH_SECRET`). In production these are
Azure App Service **Application Settings**, which Azure stores encrypted and
injects as process environment variables into the container at startup —
never written to disk in the image. This is the same mechanism used for
every credential the app needs at runtime (OAuth client secrets, payment
provider API keys, the database connection string, `BETTER_AUTH_SECRET`,
the AES-256 key used for OAuth token-at-rest encryption — see
[`4.1.3`](./4.1.3-cryptographic-operations.md)).

**Known maturity gap (already documented, not new):** Application Settings
are currently configured manually via the Azure Portal/CLI rather than
through a committed Bicep/ARM/Terraform definition. This means secret
*values* are securely stored by Azure, but *which* settings exist and how
they're provisioned isn't code-reviewed or diffable — noted previously under
[`4.1.1`](./4.1.1-tls-configuration.md) as a deployment-process maturity item,
not a secrets-storage weakness.

### 5. OAuth tokens at rest: encrypted, not just environment-protected

Beyond the app's *own* secrets, user OAuth access/refresh tokens obtained
via mailbox connections are encrypted at rest with AES-256-GCM before being
written to the database (`packages/utils/lib/token-crypto.ts`,
`packages/auth/auth.ts`'s `databaseHooks.account.create.before`/
`update.before` hooks) — see [`4.1.3`](./4.1.3-cryptographic-operations.md)
for the full inventory. This control (6.7.1) covers the application's own
server-side secrets (API keys, its signing secret); the encryption-at-rest
of *third-party* tokens the app stores is documented separately since it's a
data-protection control, not a "where do our own secrets live" one — but
it's relevant evidence that token handling in this codebase is held to a
higher bar than plaintext storage even inside the trusted database.

### Fixed — adjacent finding, outside this control's core scope: `infra/alloy-ecs` Terraform state committed to git

`infra/alloy-ecs/terraform.tfstate` and `terraform.tfstate.backup` were
tracked in git (`git ls-files infra/alloy-ecs/` listed both), despite
`.gitignore` already containing `*.tfstate`/`*.tfstate.*` patterns —
ineffective because those patterns were added after the files were already
committed, and `.gitignore` doesn't retroactively untrack existing files.

This is infrastructure for an unrelated AWS ECS sidecar (a Grafana Alloy
collector), not the `zeromail` application itself, and is a different
concern from "does the app store its secrets securely" — but reviewing it
here since it was surfaced during this control's investigation:

- **Content reviewed directly.** No live secret *value* is present. The ECS
  task definition in this state file references credentials only via an AWS
  Secrets Manager ARN — resolved by AWS at container start, never written
  into Terraform state:
  ```json
  "policy": "{\"Version\":\"2012-10-17\",\"Statement\":[{\"Effect\":\"Allow\",
  \"Action\":\"secretsmanager:GetSecretValue\",
  \"Resource\":\"arn:aws:secretsmanager:ap-south-1:522317845919:secret:popsuites/grafana-cloud-credentials-blFsbd\"}]}"
  ```
- The state file **does** expose infrastructure-recon information —
  the AWS account ID (`522317845919`), region (`ap-south-1`), and IAM
  policy/ARN structure. Not a credential leak, but committing Terraform
  state to version control is a well-known anti-pattern (state files can
  carry plaintext secrets depending on the resources they describe, and
  this repo has no guarantee a future resource added to this stack won't
  introduce one).

**Fixed:** ran `git rm --cached infra/alloy-ecs/terraform.tfstate
infra/alloy-ecs/terraform.tfstate.backup` — both files stay on disk for
whoever manages that Terraform stack, but are no longer tracked in git going
forward, so the existing `*.tfstate`/`*.tfstate.*` `.gitignore` patterns now
actually take effect for them.

**Remaining follow-up (not done here, needs the infra owner):** moving to a
remote backend (e.g. an S3 backend with encryption) is the standard
longer-term fix for this anti-pattern, so state isn't only ever a local file
in someone's working tree at all — out of scope for this pass since it
requires coordinating with whoever currently applies this stack.
