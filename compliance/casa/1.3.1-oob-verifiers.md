# CASA 1.3.1 — Authentication: Out‑of‑band verifiers random, single‑use, expiring

> **Control 1.3.1 — Authentication / Out of band verifiers shall be random and not
> reused**
>
> *Out of band verifier shall expire in a reasonable timeframe.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the out of band verifier expiration process.

---

## What an "out‑of‑band (OOB) verifier" is here

A secret delivered over a **separate channel** (email, messaging app) that the user
must return to prove control of that channel: email verification links, password‑reset
links, magic links, and one‑time codes emailed for a bot login. TOTP from an
authenticator app is **not** OOB and is out of scope for this control.

---

## Short answer (for the CASA portal)

External identity providers (**Google**, **Microsoft** OAuth 2.0) issue and expire
their own OOB verifiers. The application's own OOB verifiers — email verification
links, password‑reset links, magic links, and the Telegram‑bot login code — are each
generated per request from a cryptographically secure RNG, are single‑use (the
stored record is deleted or flagged `usedAt`/`emailVerified` on first successful use
and rejected afterwards), and expire in **5 to 60 minutes**. Codes additionally cap
verification attempts.

### Common properties against the control

- **Random:** every verifier is drawn from a CSPRNG — Web Crypto `getRandomValues`
  (Better Auth string tokens, rejection‑sampled to avoid modulo bias) or `node:crypto`
  `randomInt` / `randomBytes` (Telegram). JWT verifiers are signed with a
  high‑entropy server secret.
- **Not reused:** a new verifier is generated for every request. On the first
  successful use the backing row is deleted (`deleteVerificationValue`,
  `clearLoginState`) or flagged (`usedAt`, `emailVerified`). Every verification path
  checks `expiresAt < now` / `usedAt` and rejects stale or spent verifiers.
- **Reasonable expiry:** 5 min (magic link), 10 min (Telegram OTP), 15 min
  (Telegram link token), 60 min (email verification, password reset) — within
  NIST SP 800‑63B guidance for OOB authenticators and email action links.
- **Codes are rate‑limited:** the Telegram OTP is void after 3 wrong attempts.

### Not applicable

- **TOTP two‑factor** (`authClient.twoFactor.verifyTotp`, `twoFactor()` plugin at
  `packages/auth/auth.ts:928`) is an authenticator‑app OTP, not an OOB verifier.
- **No SMS** OOB verifier is used. `twoFactor()` is configured without an
  `otpOptions.sendOTP` handler, so no email/SMS 2FA code is issued.
