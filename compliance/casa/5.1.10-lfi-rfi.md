# CASA 5.1.10 — Data Validation and Sanitization: LFI/RFI protection

> **Control 5.1.10 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *Protect against local file inclusion or remote file inclusion attacks.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## What LFI/RFI is

Local File Inclusion happens when the server reads a file from disk (or
dynamically imports a module) using a path built, even partially, from
unvalidated user input — letting an attacker use `../`-style path traversal
to read or execute a file outside the intended directory. Remote File
Inclusion is the same idea via a remote URL treated as a local include; rarer
in Node.js apps, but checked here for completeness. When the mechanism is a
dynamic `import()` rather than a plain file read, the risk is worse than
information disclosure — the imported module's code actually executes.

---

## Short answer (for the CASA portal)

Four surfaces that read content by a path derived from request-adjacent data
were reviewed and found already protected: the avatar image-proxy route
(remote storage lookup key, not a filesystem path), attachment downloads
(fetched live from the Gmail/Outlook APIs by ID, never from disk), MDX blog
content (compiled from a fixed directory at build time), and no other
`fs.readFile`/`createReadStream` call anywhere touches user input. One
function — the i18n locale loader, which uses a *dynamic import* built from a
`locale` string — had no internal validation of its own; it was safe today
only because its two callers happen to validate first, which is a fragile
guarantee for a function whose failure mode is path-traversal-to-code-
execution. It has been hardened with a defensive allowlist check.

## Deliverable — evidence

### Fixed and hardened: `packages/i18n/lib/messages.ts`

```ts
export const importLocale = async (locale: string): Promise<Messages> => {
  return (await import(`../translations/${locale}.json`)).default as Messages;
};
```

This function had no internal validation of `locale` before using it in a
dynamic `import()` path. Its two current callers do constrain it:

- `apps/web/modules/i18n/request.ts` explicitly checks
  `routing.locales.includes(locale)` before calling, falling back to the
  default locale otherwise.
- `packages/mail/util/send.ts` → `packages/mail/util/templates.ts` type
  `locale` as `keyof typeof i18nConfig.locales` / `Locale` — a TypeScript
  union over the fixed `config.locales` keys, which prevents a caller from
  passing an arbitrary string *at compile time* but is not a runtime guard
  (a type assertion, or a future untyped caller, could bypass it).

Since `importLocale`'s mechanism is a dynamic `import()` — which executes the
imported module's code, not just reads its contents — an unvalidated
`locale` reaching this function would let an attacker traverse to and
**execute** an arbitrary file reachable from the module resolution root
(e.g. `locale = "../../../../some/other/module"`), not merely read one. The
function was safe in practice only by accident of both current callers'
discipline, not by its own construction.

**Fix applied:**

```ts
export const importLocale = async (locale: string): Promise<Messages> => {
  if (!(locale in config.locales)) {
    throw new Error(`Unknown locale: ${locale}`);
  }
  return (await import(`../translations/${locale}.json`)).default as Messages;
};
```

`config.locales` (`packages/i18n/config.ts`) is a small, fixed, hardcoded
object — the authoritative allowlist of valid locales. The function now
throws on any value outside that allowlist, before the dynamic import ever
runs, regardless of what any current or future caller does. Both existing
call sites are unaffected — they already only ever pass valid locales, so
this is a no-op for legitimate traffic.

**Verified in this session**: `importLocale("en")` still succeeds;
`importLocale("../../../../etc/passwd")`, `importLocale("../../../package")`,
and `importLocale("en/../../../secrets")` all now throw `Unknown locale: ...`
before reaching the dynamic import, rather than attempting to resolve a
traversal path.

### Already protected: image-proxy route

`apps/web/app/image-proxy/[...path]/route.ts` (reviewed in
[`5.1.5`](./5.1.5-ssrf.md)) resolves the requested path via `getSignedUrl()`,
which always calls a remote storage service (S3 or Azure Blob) using the path
as a lookup key inside an HTTP API request (`GetObjectCommand` / a SAS URL) —
never a local `fs` read. A `../` in the key is treated as a literal character
in an object key by the storage provider's API, not filesystem traversal.
`bucket` is additionally constrained to the literal `"avatars"`.

### Already protected: attachment downloads

`packages/api/modules/payment-tracking/procedures/get-attachment.ts` fetches
email attachments live from the Gmail/Outlook APIs by `attachmentId`, after
verifying the requesting user owns the associated mailbox
(`verifyMailboxOwnership`). No local filesystem path is ever constructed from
the attachment ID.

### Already protected: MDX blog content

`content-collections` (`apps/web/content-collections.ts`) resolves a fixed
`directory`/`include` glob at **build time**, producing a static, pre-compiled
dataset. Runtime page rendering looks up entries by slug/path fields within
that generated dataset — it never re-reads the filesystem using a
request-supplied path.

### No other file-read-by-user-input pattern

A repository-wide search for `fs.readFile`/`fs.readFileSync`/`createReadStream`
combined with any request-derived value found no matches in application
code — the only hits anywhere are test/dev-tooling `.env` loaders reading a
fixed, hardcoded path, unrelated to request input.
