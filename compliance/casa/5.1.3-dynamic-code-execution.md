# CASA 5.1.3 — Data Validation and Sanitization: Avoid dynamic code execution

> **Control 5.1.3 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *Avoid the use of eval() or other dynamic code execution features. When there
> is no alternative, any user input is sanitized and sandboxed before being
> executed.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

`eval()`, `new Function()`, string-argument timers, `vm.runInContext`/`vm.Script`,
dynamic `require()`, and `child_process` shell execution are all **absent** from
this codebase — a repo-wide search found zero occurrences of any of them. The one
feature where a naive implementation might plausibly reach for `eval()` — the
mailbox rules engine, which evaluates user-authored conditions like "subject
contains X" against incoming email — instead uses plain string methods
(`.includes()`) and a small set of hardcoded regex literals. No user input is ever
executed as code anywhere in the application.

## Deliverable — evidence

### No dynamic-execution primitives anywhere

A repository-wide search (excluding `node_modules`) found:

| Pattern | Result |
|---|---|
| `eval(` | Zero matches |
| `new Function(` / `Function(` constructor form | Zero matches |
| `setTimeout`/`setInterval` with a string (rather than function) argument | Zero matches |
| `vm.runInContext`, `vm.Script` (Node's `vm` module) | Zero matches |
| Dynamic `require()` (non-literal argument) | Zero matches |
| `child_process` (`exec`/`execSync`/`spawn`/`spawnSync`) | Zero matches — the application never shells out |

Every `import()` call in the codebase uses a literal or enum-bounded specifier —
locale JSON files keyed by the app's own locale enum
(`packages/i18n/lib/messages.ts`), lazy-loaded cron job handlers with literal
relative paths (`packages/api/index.ts`), and literal third-party module names.
None interpolate a request body, query parameter, email content, or LLM output
into an import specifier.

### The mailbox rules engine — the one plausible risk area, and why it's safe

This app lets users define inbox rules with conditions like "if sender contains
X" or an AI-evaluated natural-language instruction. A rules engine like this is
exactly the kind of feature that sometimes gets implemented by `eval()`-ing a
user-supplied expression — checked specifically and found not to be the case here.

`packages/api/modules/mailboxes/lib/rule-evaluator.ts:277-314` — static
conditions (`from`/`to`/`subject`) are evaluated with plain, safe string
comparison:

```ts
if (condition.static?.subject) {
  const pattern = condition.static.subject.toLowerCase();
  const matched = email.subject.toLowerCase().includes(pattern);
  // ...
}
```

No dynamic regex is built from the user's condition text, no `eval()`, no
sandboxed-but-still-dynamic execution.

`rule-evaluator.ts:350-357` — a performance short-circuit for the "AI condition"
rule type matches the instruction text against a **fixed, hardcoded** array of
regex literals (`/\bfrom\s+([a-z0-9._-]+)/`, `/\bsender\s+is\s+([a-z0-9._-]+)/`,
etc.) before falling back to an actual LLM call. The regex patterns themselves are
compile-time constants; only the *string being searched* (the user's instruction)
is dynamic, which is the normal, safe use of `RegExp.prototype.match` — not
dynamic code construction.

The "AI condition" itself is never executed as code: the user's instruction text
is sent as a prompt to Gemini (`generateObject` from `@ai-sdk/google`) and the
model returns a structured `{ match: boolean }` object, parsed and validated —
this is prompt construction and schema-validated LLM output, with no code
execution involved on either side.

### `RegExp` construction from dynamic strings — checked for ReDoS, found low-risk

Two call sites build a `RegExp` from a template-interpolated string rather than a
literal, which is worth a note even though it's a distinct concern from
eval/dynamic-execution:

- `packages/api/modules/mailboxes/lib/header-parser.ts:73` — `` new
  RegExp(`\\b${method}=([a-z]+)`, "i") `` — `method` is always one of three
  hardcoded literals (`"spf"`, `"dkim"`, `"dmarc"`) supplied by internal call
  sites, never user input.
- `apps/web/modules/shared/lib/content.ts:35` — `` new RegExp(`^${subPath}[/]*`)
  `` — `subPath` derives from static documentation/MDX file paths resolved at
  build time, not request input.

Neither is reachable with attacker-controlled input, so neither presents a ReDoS
or injection risk.
