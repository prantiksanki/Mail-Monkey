# CASA 5.1.2 — Data Validation and Sanitization: Open-redirect protection

> **Control 5.1.2 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *URL redirects and forwards are limited to allowlisted URLs or a warning is
> displayed when redirecting to untrusted content.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

A code review found one real open-redirect gap: the post-login/signup redirect
target (`redirectTo` query param) was read directly from the URL and passed
unvalidated into a client-side navigation. This has been fixed with a same-origin
path allowlist (`getSafeRedirectPath`) applied at all three call sites. Every other
redirect surface in the app — including Better Auth's own OAuth/magic-link/
password-reset `callbackURL` handling — was already protected, either by
server-side `trustedOrigins` enforcement or by using hardcoded/server-derived
targets rather than raw user input.

---

## Deliverable — findings and fix

### Gap found and fixed: `redirectTo` on the auth forms

`LoginForm.tsx`, `OtpForm.tsx`, and `SignupForm.tsx`
(`apps/web/modules/saas/auth/components/`) each read a `redirectTo` query
parameter and used it, unvalidated, as a client-side redirect target:

```ts
const redirectTo = searchParams.get("redirectTo");
const redirectPath = invitationId
  ? `/organization-invitation/${invitationId}`
  : (redirectTo ?? config.saas.redirectAfterSignIn);
// ...
router.replace(redirectPath);
```

Under normal use `redirectTo` is set safely by `apps/web/proxy.ts` from the
current request's own path (`withQuery("/auth/login", { redirectTo: pathname })`
— same-origin by construction). But an attacker doesn't need the proxy to set it:
a direct link such as

```
https://popsuites.ai/auth/login?redirectTo=https://evil.example/phishing
```

or a protocol-relative variant (`redirectTo=//evil.example`) would, after the
victim authenticates, cause `router.replace()` to navigate them off-site — a
classic open redirect, exploitable for phishing since the link starts on the
genuine login page.

**Fix:** `apps/web/modules/shared/lib/safe-redirect.ts` — `getSafeRedirectPath(candidate, fallback)`:
- Returns `fallback` for `null`/empty input.
- Rejects any value containing `://`.
- Rejects any value not starting with exactly one `/`, and specifically rejects
  `//...` and `/\...` (both of which browsers resolve as protocol-relative — an
  effective absolute URL to a different host, the classic way to smuggle an
  external redirect past a naive "must start with `/`" check).
- Otherwise returns the candidate unchanged — a same-origin relative path.

Applied at all three call sites in place of the raw `redirectTo ?? fallback`
expression. Verified in this session with 8 cases (`https://evil.example`,
`//evil.example`, `/\evil.example`, `http://evil.example/x`, `null`, empty
string, a legitimate nested path, and the invitation-redirect path) — all
malicious/malformed inputs fall back to the safe default, all legitimate
relative paths pass through unchanged.

The `invitationId` branch (`` `/organization-invitation/${invitationId}` ``)
needed no change: `invitationId` is only ever used as a route-param lookup key
against the invitation table, not interpolated as a redirect target string an
attacker could hijack with a full URL — the template literal always produces a
same-origin path regardless of what `invitationId` contains.

### Already protected: Better Auth's `callbackURL` / `redirectTo` / `errorCallbackURL` / `newUserCallbackURL`

These parameters — used across OAuth sign-in (`SocialSigninButton.tsx` and every
mailbox-connect flow), magic-link, email-verification, and password-reset —
are validated **server-side** by Better Auth itself before any redirect happens.
`packages/auth/auth.ts` sets `trustedOrigins: [appUrl, ...extraTrustedOrigins]`
(the app's own origin plus any origins from `BETTER_AUTH_TRUSTED_ORIGINS`), and
the installed library's `originCheckMiddleware`
(`better-auth/dist/api/middlewares/origin-check.mjs`) runs on every non-GET auth
request, checking `body.callbackURL`/`query.callbackURL`/`body.redirectTo`/
`body.errorCallbackURL`/`body.newUserCallbackURL` against `isTrustedOrigin(...)`
and throwing `APIError("FORBIDDEN")` on any mismatch. No code change was needed
here — this is allowlist enforcement working as intended.

### Reviewed, not applicable

Every other `redirect(`/`router.push(`/`window.location.href =` call site in the
app (`proxy.ts`'s own hardcoded redirects, `NavBar.tsx`, `UserMenu.tsx`,
`ActiveSessionsBlock.tsx`, `PricingTable.tsx`, the organization-invitation page,
payment checkout/portal links) uses a hardcoded relative path, a server-derived
value (e.g. a database-looked-up slug), or a URL returned directly from a
trusted payment provider's server response — none incorporate raw,
attacker-suppliable query/header/body text as a redirect target.

### On the listed deliverable (DAST scan)

As with [`5.1.1`](./5.1.1-parameter-pollution.md), the checklist's deliverable
text calls for an external dynamic scan, tracked as the same open item under
[`3.1.1`](./3.1.1-urls-no-auth-material.md). This write-up documents the
code-level fix and evidence that should make an open-redirect finding absent
from such a scan going forward.
