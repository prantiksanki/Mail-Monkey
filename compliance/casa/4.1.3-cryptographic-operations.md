# CASA 4.1.3 — Communications: Cryptographic operations inventory

> **Control 4.1.3 — Communications / Protect confidential data through strong
> cryptography**
>
> *No instances of weak cryptography which meaningfully impact the confidentiality
> or integrity of data.*
>
> **Deliverables**
> 1. Describe any situations in which your application uses the following
>    cryptographic operations: Encryption or decryption; Hashing; MAC or HMAC.
> 2. For each of these operations, briefly describe how your application performs
>    the cryptographic operation including: chosen cryptographic algorithms; key
>    size and mechanism of generation; IV size and mechanism of generation (if
>    applicable); key management (storage, rotation, and expiration).

---

## Short answer (for the CASA portal)

The application uses cryptography in five places: password hashing (scrypt, see
[`1.1.3`](./1.1.3-password-storage.md)), OOB verifier generation (CSPRNG, see
[`1.3.1`](./1.3.1-oob-verifiers.md)–[`1.3.4`](./1.3.4-oob-verifier-brute-force.md)),
JWT verification of Google's OAuth idToken (RS256, Google's public JWKS),
session/cookie integrity (Better Auth's HMAC-SHA256), OAuth token encryption at
rest (AES-256-GCM, added as part of this control's review), and webhook signature
verification (HMAC-SHA256, several payment providers plus Telegram). No weak
algorithm (MD5, SHA-1, RC4, DES) is used anywhere in application code.

## Deliverable — full inventory

### 1. Password hashing — scrypt

Fully documented in [`1.1.3-password-storage.md`](./1.1.3-password-storage.md).
Summary: Better Auth's default scrypt hasher, `N=16384, r=16, p=1, dkLen=64`
(~32 MiB memory cost), unique 128-bit CSPRNG salt per password, constant-time
verification. Not re-derived here.

### 2. OOB verifier generation — CSPRNG

Fully documented in [`1.3.1`](./1.3.1-oob-verifiers.md),
[`1.3.3`](./1.3.3-oob-verifier-randomness.md), and
[`1.3.4`](./1.3.4-oob-verifier-brute-force.md): magic-link tokens, password-reset
tokens, email-verification JWTs, and Telegram OTP/link tokens. Not re-derived here.

### 3. Google OAuth idToken verification — JWT, RS256

- **Where:** `packages/auth/auth.ts` (`createMailboxAfterAccountCreation`, Google
  branch), verifying the idToken Google returns during OAuth sign-in.
- **Algorithm:** RS256, explicitly pinned via `algorithms: ["RS256"]` — no
  algorithm-confusion risk (the verifier will not accept a token signed with a
  different/weaker algorithm even if an attacker requests one).
- **Key:** Google's own public JWKS, fetched via `createRemoteJWKSet(new
  URL("https://www.googleapis.com/oauth2/v3/certs"))` (`jose` library) — a remote,
  rotating key set managed entirely by Google; this application holds no private
  key material for this verification.
- **Failure handling:** a verification failure throws and is logged; the caller
  treats it as account-creation failure rather than silently accepting an
  unverified payload.

### 4. Session and cookie-cache integrity — HMAC-SHA256

- **Where:** Better Auth's session token cookie and `cookieCache` (compact
  strategy, the default and what this app uses —
  `packages/auth/auth.ts`, `session.cookieCache = { enabled: true, maxAge: 60 }`).
- **Algorithm:** HMAC-SHA256, computed via WebCrypto (`crypto.subtle.sign`),
  verified via `crypto.subtle.verify` (constant-time).
- **Key:** `BETTER_AUTH_SECRET` (env var) — the same secret also signs the
  email-verification JWT (see `1.3.1`). A single long-lived key; no rotation
  mechanism exists in code. Rotating it invalidates every active session and any
  pending email-verification/reset token — a real key-management cost, noted here
  as the tradeoff of the current single-secret design rather than a defect.
- **Confidentiality note:** the cookie is signed, not encrypted — its contents
  (session id, user id) are readable by the browser but tamper-proof.
  Confidentiality in transit relies on HTTPS (see
  [`4.1.1`](./4.1.1-tls-configuration.md)) and the `httpOnly`/`Secure` cookie flags.

### 5. OAuth token encryption at rest — AES-256-GCM (new)

Added as part of this control's review. `Account.accessToken`, `refreshToken`, and
`idToken` (`packages/database/prisma/schema.prisma`) previously stored these values
as plaintext, which contradicted the public claim on the marketing security page
(`apps/web/app/(marketing)/[locale]/security/page.tsx`) that tokens are "encrypted
at rest using AES-256." That gap is now closed:

- **Implementation:** `packages/utils/lib/token-crypto.ts` — `encryptToken` /
  `decryptToken`.
- **Algorithm:** AES-256-GCM (`node:crypto` `createCipheriv`/`createDecipheriv`,
  algorithm `"aes-256-gcm"`).
- **Key size:** 256 bits (32 bytes).
- **IV:** 96 bits (12 bytes, the standard/recommended size for GCM), generated
  fresh per encryption call via `crypto.randomBytes(12)` — never reused.
- **Authentication tag:** GCM's 128-bit tag is stored alongside the IV and
  ciphertext (`<iv>:<authTag>:<ciphertext>`, each base64) and verified on every
  decrypt via `setAuthTag`/`decipher.final()`, which throws if the tag doesn't
  match — see [`4.1.4`](./4.1.4-secure-crypto-failures.md) for why this matters for
  failing securely.
- **Key management:** `OAUTH_TOKEN_ENCRYPTION_KEY`, a base64-encoded 32-byte key
  supplied via environment variable (generated with `openssl rand -base64 32`, see
  `.env.local.example`). Like `BETTER_AUTH_SECRET`, this is a single long-lived key
  with no in-code rotation mechanism; rotating it requires re-encrypting every
  stored token (the same migration script used to backfill existing plaintext
  tokens — `tooling/scripts/src/encrypt-existing-oauth-tokens.ts` — can be adapted
  for a future rotation by decrypting with the old key and re-encrypting with the
  new one).
- **Coverage:** every write path (Better Auth's own account-linking flow, via
  `databaseHooks.account.create.before`/`update.before`; and this app's own direct
  token-refresh writes in `google-auth.ts`, `microsoft-auth.ts`, `zoom-client.ts`,
  `zoho-meeting-client.ts`) and every read path that uses the token value (as
  opposed to merely checking presence) now encrypts/decrypts explicitly. Existing
  plaintext rows were migrated via the script above (verified: 4/4 accounts in the
  local dev database migrated and round-trip successfully).

### 6. Webhook signature verification — HMAC-SHA256

| Integration | Where | Comparison |
|---|---|---|
| Creem | `packages/payments/provider/creem/index.ts` | `timingSafeEqual` (fixed as part of this control — see [`4.1.4`](./4.1.4-secure-crypto-failures.md)) |
| LemonSqueezy | `packages/payments/provider/lemonsqueezy/index.ts` | `timingSafeEqual` (already correct) |
| Stripe | `packages/payments/provider/stripe/index.ts` | Delegated to the Stripe SDK's `webhooks.constructEventAsync` (HMAC-SHA256 + constant-time compare, library-internal) |
| Polar | `packages/payments/provider/polar/index.ts` | Delegated to `@polar-sh/sdk`'s webhook verifier |
| DodoPayments | `packages/payments/provider/dodopayments/index.ts` | Delegated to the DodoPayments SDK's Svix-style `webhooks.unwrap` |
| Telegram bot | `packages/api/modules/telegram/webhook.ts` | Plain shared-secret header check, `timingSafeEqual` (fixed as part of this control) |

All webhook secrets come from environment variables (`CREEM_WEBHOOK_SECRET`,
`LEMONSQUEEZY_WEBHOOK_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, etc.) — no rotation
mechanism in code; rotation is a manual env-var change paired with re-registering
the new secret with the provider.

### Confirmed absent — no weak cryptography

A full-repository search found **zero** occurrences of MD5, SHA-1, RC4, DES, or any
other deprecated/weak algorithm in application code (only transitive lockfile
entries for unrelated AWS SDK internals, never executed application logic). No
symmetric encryption existed anywhere in custom code prior to this control's
review — the AES-256-GCM addition above is new, not a replacement of a weaker
scheme.
