# CASA 3.1.1 — Session Management: URLs shall not expose authentication material

> **Control 3.1.1 (Session Management) — URLs shall not expose authentication
> material**
>
> *The application shall not reveal passwords or session tokens in URL parameters.
> In cases where the application provides an API, the application shall prevent (or
> give developers an option to prevent) exposing sensitive information like API keys
> or session tokens within the URL query strings.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing (DAST) Guidance. Scanning may be performed by the developer or
>    by an authorized testing lab.
>
> *(Control ID follows the CASA "Session Management" section; the assessor's exact
> numbering may differ.)*

## Code‑level self‑assessment

### Session tokens — carried only in cookies

Sessions are managed by Better Auth `1.4.7`. The session token lives in a cookie,
never a URL:

- `packages/auth/auth.ts:547` — `advanced.useSecureCookies: process.env.NODE_ENV === "production"`.
- Better Auth cookie defaults (`node_modules/better-auth/dist/cookies/index.mjs:27‑30`):
  `httpOnly: true`, `sameSite: "lax"`, `secure` in production, `path: "/"`.
- `session.cookieCache` (`packages/auth/auth.ts:563`) stores the cached session in a
  signed cookie — again, not a URL parameter.
- The client reads the session via `authClient` / `useSession`, which call the
  cookie‑authenticated `/api/auth/get-session` endpoint. No token is ever placed in
  `window.location`, a link `href`, or a redirect target.

### Passwords — never in a request URL

- Password login is disabled (`packages/auth/config.ts:16` → `enablePasswordLogin: false`).
- Where password endpoints exist, Better Auth accepts credentials only in a
  **POST body** (`/sign-in/email`, `/reset-password`), never in the query string.
- Repository search for a password read from a query string
  (`query.password`, `searchParams.get("password")`, …): **no matches**.

### API keys / service secrets — header only

| Secret | Transport | Reference |
|--------|-----------|-----------|
| `CRON_SECRET` (internal / cron routes) | `Authorization: Bearer …` header | `packages/api/index.ts:81‑85`, `:299`, `:314`, `:329`, `:344`, `:359` |
| `METRICS_SCRAPE_TOKEN` (`/api/metrics`) | `Authorization: Bearer …` header | `apps/web/app/api/metrics/route.ts:9` |
| oRPC API (`/api/rpc/*`) | session cookie | Better Auth middleware |
| Provider webhook secrets (Gmail, Outlook, payments, Telegram) | request header / signed payload | `packages/api/index.ts` webhook handlers |

There is **no application API‑key scheme** that a developer could accidentally place
in a query string; the `better-auth` `apiKey` plugin is not enabled. Repository
search for `query.apiKey` / `api_key` / `access_token` reads from a URL: **no
matches**.

### Tokens that *do* appear in URL query strings — and why they are out of scope

| Parameter | Where | Nature | Assessment |
|-----------|-------|--------|------------|
| `?code=`, `?state=` | OAuth redirect back from Google / Microsoft to `/api/auth/callback/:id` | Standard OAuth 2.0 **authorization code** — single‑use, ~seconds TTL, exchanged server‑side for tokens; `state` is a CSRF nonce | Not a password, session token, or API key. This is the OAuth 2.0 spec flow; the code is useless after the server exchange. |
| `?token=` | Email‑verification, password‑reset, and magic‑link action links | **Single‑use out‑of‑band verifier**, 5–60 min TTL, deleted on use (see [`1.3.1-oob-verifiers.md`](./1.3.1-oob-verifiers.md)) | Not a session token or password. Emailed action links are the accepted pattern; the value grants no session until redeemed and cannot be replayed. |
| `?invitationId=`, `?email=` | Organisation‑invitation links (`packages/auth/auth.ts:912‑913`) | Opaque row ID + the invitee's own email (PII, not a secret); acceptance still requires authentication | Not authentication material. Organisations are disabled (`packages/auth/config.ts:34`). |

### Leakage controls in place

- `Referrer-Policy: strict-origin-when-cross-origin` (`apps/web/next.config.ts`
  `headers()`) — strips path + query from the `Referer` header on cross‑origin
  navigation, so even the action‑link `?token=` is not leaked to third parties.
- `Strict-Transport-Security: max-age=63072000; includeSubDomains` — URLs are only
  ever sent over TLS.
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` also set.

## DAST scan — method and results

### Method (per ADA DAST guidance)

- **Tool:** OWASP ZAP (baseline scan for the automated pass; full/active scan for a
  thorough run). Burp Suite Professional or an equivalent is acceptable if the lab
  prefers.
- **Target:** the deployed staging instance over HTTPS.
- **Auth context:** provide ZAP an authenticated session (context + session
  management via the Better Auth cookie) so post‑login pages, the oRPC API, and the
  action‑link flows are all crawled.
- **Focus checks for this control:**
  - Alert **10024 – Information Disclosure: Sensitive Information in URL**.
  - Alert **10025 – Information Disclosure: Sensitive Information in HTTP Referrer Header**.
  - Session‑token handling: confirm ZAP identifies the session as cookie‑based, not
    URL‑based.
  - Manually confirm no `Set-Cookie`‑issued token is subsequently reflected into a
    redirect `Location` query string.
- **Scope note for the triage:** OAuth `code`/`state` and the emailed `token=`
  action‑link parameters are expected to appear and are documented above as
  out‑of‑scope for "session tokens / passwords / API keys"; everything else flagged
  under 10024/10025 is in scope.

### Pre‑scan remediation (from an exploratory ZAP run)

An exploratory ZAP pass was run before the formal lab scan. Findings and actions:

| Alert | Finding | Action |
|-------|---------|--------|
| **10024 – Sensitive Information in URL** | `/contact` — the marketing contact form has no `method`, so ZAP's no‑JS spider submits it as `GET`, placing `name`, `email`, `message` in the query string. (Real users submit via a JS `POST` through oRPC; the email is PII, not a session token/password, so severity is low — but it is a valid 3.1.1 finding.) | **Fixed** — `method="post"` added to `ContactForm.tsx` and `ProfileContactForm.tsx` (`apps/web/modules/marketing/home/components/ContactForm.tsx`, `apps/web/modules/marketing/profile/components/ProfileContactForm.tsx`). The no‑JS fallback is now a POST; the JS path is unchanged. |
| **10037 – `X-Powered-By` leak** | Next.js advertised itself in the response header. | **Fixed** — `poweredByHeader: false` in `apps/web/next.config.ts`. |
| **10063 – Permissions‑Policy missing** | No `Permissions-Policy` header. | **Fixed** — `Permissions-Policy: camera=(), geolocation=(), browsing-topics=()` added in `apps/web/next.config.ts` `headers()`. `microphone` is intentionally left at the browser default (`self`) because the marketing voice demo calls `getUserMedia`. |
| **10010 – Cookie No `HttpOnly`** | The `NEXT_LOCALE` locale‑preference cookie on the marketing pages is readable by JavaScript. | **Accepted, no change** — `NEXT_LOCALE` carries no authentication material; it is a UI language preference and is read client‑side by the oRPC client (`apps/web/modules/shared/lib/orpc-client.ts:36`) to set the request locale header, so it must stay JS‑readable. Out of scope for 3.1.1 (not a session token / password / API key). |
| **10038 / 10055 – CSP missing / wildcard directives** | No `Content-Security-Policy`; some directives permissive. | **Deferred** — a correct CSP for this app must enumerate Google Tag Manager / GA4, Polar checkout, Cloudflare, and font/CDN origins, and needs staging verification to avoid breaking those. Tracked as hardening follow‑up; per ADA guidance this is not an AL1 blocker for control 3.1.1. |

### How to run the formal scan

1. **Baseline (unauthenticated):**
   ```bash
   docker run --rm -v "$(pwd):/zap/wrk/:rw" ghcr.io/zaproxy/zaproxy:stable \
     zap-baseline.py -t https://STAGING_URL \
     -r zap-baseline-report.html -J zap-baseline-report.json -I
   ```
2. **Authenticated full scan:** log into staging via Google/Microsoft in a browser,
   copy the value of the `__Secure-better-auth.session_token` cookie, and run the
   ZAP Automation Framework plan with a `replacer` job that injects
   `Cookie: __Secure-better-auth.session_token=<value>` on every request, followed by
   `spider` + `spiderAjax` + `activeScan` + `report` (traditional‑html and
   traditional‑json). Keep `spiderAjax` so the client‑rendered `/app/*` routes are
   crawled.
3. In the report, check alerts **10024** and **10025**; for every hit, record the URL
   and classify it as in‑scope (session token / password / API key → must fix) or
   out‑of‑scope (OAuth `code`/`state`, emailed action‑link `token`).
