# CASA 1.3.4 — Authentication: Out‑of‑band verifiers resistant to brute force

> **Control 1.3.4 — Authentication / Out of band verifiers shall be random and not
> reused**
>
> *Out of band verifier shall be resistant to brute force attacks.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the algorithm used to generate initial authentication
>    codes and also of any rate‑limiting applied during the application's initial
>    authentication code validation process.

---

## Short answer (for the CASA portal)

Brute‑force resistance rests on two layers. **Entropy:** string verifiers carry
143–192 bits of CSPRNG output and the email‑verification link is an unforgeable
HMAC‑SHA‑256 JWT, so guessing is computationally infeasible. **Rate limiting:** every
validation request passes through a global limiter (100 req/min/IP) and, on the auth
namespace, a stricter auth limiter (10 req/min/IP), plus Better Auth's own
production rate limiter (100 req/10 s/IP globally; **3 req/10 s** for sign‑in/sign‑up
and for every `/two-factor/*` endpoint). The one low‑entropy verifier — the 6‑digit
Telegram login code — additionally has a hard cap of **3 attempts** per issued code,
after which the code is destroyed, and a 10‑minute expiry.

## Deliverable 2a — Algorithm used to generate the codes

Full detail is in [`1.3.3-oob-verifier-randomness.md`](./1.3.3-oob-verifier-randomness.md).
In brief, all values come from a CSPRNG:

| Verifier | Generator | Search space |
|----------|-----------|--------------|
| Magic‑link token | `generateRandomString(32,"a-z","A-Z")` — Web Crypto `getRandomValues`, rejection‑sampled | ~182 bits |
| Password‑reset token | `generateId(24)` over `a‑z A‑Z 0‑9` — same CSPRNG | ~143 bits |
| Email‑verification link | HS256 JWT signed with `BETTER_AUTH_SECRET` | Unforgeable without the server secret |
| Telegram login OTP | `node:crypto` `randomInt(100000, 1000000)` | 9 × 10⁵ values (6 digits) |
| Telegram account‑link token | `node:crypto` `randomBytes(24)` → base64url | 192 bits |

For the string tokens and the JWT, the search space alone (≥ 2¹⁴³) makes brute force
infeasible before the token's 5–60 minute expiry; rate limiting below is
defence‑in‑depth. For the 6‑digit OTP the attempt cap and expiry are the primary
control.

## Deliverable 2b — Rate limiting during code validation

All `/api/*` traffic is served by the Hono app (`apps/web/app/api/[[...rest]]/route.ts`
→ `@repo/api`). Middleware chain (`packages/api/index.ts:140‑149`):

### Layer 1 — application limiters (`packages/api/lib/rate-limit.ts`)

`hono-rate-limiter`, keyed by client IP (`getClientIp` — Azure/Railway‑aware,
strips the source port so counters accumulate). `Retry-After` + HTTP 429 on limit;
logged as `[rate-limit] exceeded`.

| Limiter | Scope (`index.ts`) | Limit |
|---------|--------------------|-------|
| `globalLimiter` | every path (`:140`) | **100 / 60 s / IP** |
| `authLimiter` | `/auth/*` (`:141`) — covers `/api/auth/verify-email`, `/api/auth/reset-password`, `/api/auth/magic-link/verify`, `/api/auth/two-factor/*` | **10 / 60 s / IP** |
| `telegramWebhookLimiter` | `/webhooks/telegram` (`:145`) — where the Telegram OTP is submitted | **200 / 60 s / IP** |

Bypassed only when `NODE_ENV !== "production"` (unless `RATE_LIMIT_IN_DEV=1`), or in
production with the explicit `DISABLE_RATE_LIMIT=1` break‑glass flag; `/api/health`
and internal cron paths are excluded.

### Layer 2 — Better Auth built‑in rate limiter

No `rateLimit` option is set in `packages/auth/auth.ts`, so Better Auth `1.4.7`
defaults apply (`node_modules/better-auth/dist/context/create-context.mjs:131‑136`):

- **`enabled: isProduction`** — on in every deployed environment.
- Keyed by `ip + path` (`api/rate-limiter/index.mjs:96`); 429 + `Retry-After` on
  breach.
- Global default: **100 requests / 10 s**.
- Special rule (`api/rate-limiter/index.mjs:148‑156`): **3 requests / 10 s** for
  `/sign-in*`, `/sign-up*`, `/change-password*`, `/change-email*`.
- Two‑factor plugin rule (`plugins/two-factor/index.mjs:195‑201`): **3 requests /
  10 s** for every `/two-factor/*` path — this throttles `verify-totp` and
  `verify-backup-code`.

### Layer 3 — per‑verifier logic

| Verifier | Additional control | Reference |
|----------|--------------------|-----------|
| Telegram login OTP | **Hard cap of 3 attempts** per issued code, then `clearLoginState` deletes it (`MAX_OTP_ATTEMPTS = 3`); code also expires after 10 min | `packages/api/modules/telegram/service.ts:107`, `:1950‑1951`, `:1967` |
| Password‑reset / magic‑link / verification token | Single‑use — the row is deleted (`deleteVerificationValue`) or the `emailVerified` flag blocks reuse on first success; expired/spent tokens are rejected before any comparison | `reset-password.mjs:148`,`:158`; `magic-link/index.mjs:120‑124`; `email-verification.mjs:105`,`:252` |
| TOTP two‑factor | Time‑boxed to a 30 s step; a 6‑digit guess must also beat the 3/10 s plugin limiter | `plugins/two-factor/*` |

### Worked resistance estimate

- **String tokens / JWT:** ≥ 2¹⁴³ search space; at the most permissive applicable
  limit (100/10 s) an attacker covers < 2³⁰ guesses before expiry — a vanishing
  fraction. Infeasible.
- **TOTP (10⁶ space):** ≤ 18 guesses/min after the 3/10 s limiter; the code rotates
  every 30 s, so the effective space never shrinks. Infeasible.
- **Telegram OTP (9 × 10⁵ space):** at most **3 guesses total** per code before it is
  destroyed → ≈ 1‑in‑300 000 chance per issued code; a new code needs a fresh
  `/login` and is rate‑limited by `telegramWebhookLimiter`.
