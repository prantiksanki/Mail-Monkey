# CASA 5.1.8 — Data Validation and Sanitization: Database injection protection

> **Control 5.1.8 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *Protect against database injection attacks.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

All database access goes through Prisma's query builder, which is
automatically parameterized and safe from SQL injection by construction.
Exactly one raw-SQL call exists anywhere in the codebase, and it uses Prisma's
safe tagged-template form (`` $queryRaw`...` ``), which parameterizes every
interpolated value rather than concatenating it into the query string. The
actually-dangerous escape hatches (`$queryRawUnsafe`, `$executeRawUnsafe`)
are not used anywhere.

---

## Deliverable — evidence

### Database access is exclusively through Prisma's parameterized query builder

Per this repository's own API conventions
(`.claude/rules/api-conventions.md`: "Database access goes through the client
imported from `@repo/database`"), every query in the codebase uses Prisma's
standard methods — `findUnique`, `findMany`, `create`, `update`, `groupBy`,
and so on. These methods build parameterized SQL internally; there is no code
path where a value is ever concatenated into a query string when using them.

### The one raw-SQL call site — safe, parameterized tagged template

`packages/database/prisma/queries/mailbox-stats.ts:127-129`:

```ts
db.$queryRaw<
  Array<{ bucket: Date; status: string; count: bigint }>
>`SELECT date_trunc('day', "createdAt") AS bucket, status, COUNT(*)::bigint AS count
  FROM rule_execution_log
  WHERE "mailboxId" = ${mailboxId} AND "createdAt" >= ${start7d}
  GROUP BY bucket, status ORDER BY bucket ASC`
```

This is Prisma's **tagged-template** form of `$queryRaw` — every `${...}`
interpolation inside a tagged template is converted by Prisma's tag function
into a genuine bound parameter sent separately from the query text, exactly
as a parameterized query built with a raw `pg` client would be. Neither
`mailboxId` nor `start7d` is ever concatenated into the SQL string; both are
values, not identifiers, and both flow through parameter binding regardless
of what they contain. This is the one and only raw-SQL call anywhere in the
reachable codebase, and it is safe.

### The unsafe variants are not used anywhere

A repository-wide search found **zero** occurrences of `$queryRawUnsafe` or
`$executeRawUnsafe` — the two Prisma methods that accept a plain string and
are *not* automatically parameterized, where string-concatenating user input
would be classic SQL injection. `$executeRaw` (tagged or unsafe) does not
appear anywhere either.

### No dynamic identifier (column/table name) interpolation

A separate, related risk — even with Prisma's safe value-parameterization,
building a *column name* or *table name* dynamically from user input as a raw
string fragment would still be unsafe (parameterization only protects values,
not identifiers). Checked and not present: every `orderBy` clause in the
codebase uses a fixed, hardcoded field name (e.g. `{ id: "asc" }`,
`{ internalDate: "desc" }`, `{ _count: { ruleId: "desc" } }`). User-supplied
search terms (e.g. mailbox email search) are passed as Prisma `where`-filter
*values*, still going through the query builder — never as raw SQL fragments
or interpolated column names.

### No ORM bypass

No direct `pg`/`node-postgres` client query exists anywhere outside Prisma.
Migration SQL under `packages/database/prisma/migrations/` is standard DDL,
applied at deploy time by the Prisma CLI — not a runtime-reachable code path
that could process live user input.

### Legacy Drizzle setup — confirmed dead code, out of scope

`packages/database/drizzle/` contains an unused, legacy ORM setup. Confirmed
by direct search: nothing in the application imports from it
(`packages/database/index.ts` only exports `./prisma`), so it is not part of
any live request path. For completeness, its own `sql` tagged-template usages
(in `drizzle/schema/sqlite.ts`) are hardcoded `CURRENT_TIMESTAMP` column
defaults with no interpolated variables at all — not an injection vector even
hypothetically, and irrelevant regardless since the module is unreachable.
