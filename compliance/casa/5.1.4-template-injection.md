## What server-side template injection (SSTI) is

SSTI happens when attacker-controlled content becomes part of a template's
*source* before it's compiled — not merely data passed into an already-compiled
template. A vulnerable pattern looks like `Handlebars.compile(userSuppliedString)`
or a template literal whose user-supplied portion is itself re-parsed as template
syntax: an attacker sets their display name to something like
`{{constructor.constructor('return process.env')()}}` and, if that string is fed
into a template compiler, it executes as template directives rather than
rendering as plain text.

---

## Short answer (for the CASA portal)

This application does not use a string-based template-compilation engine
anywhere (no Handlebars, EJS, Mustache, Nunjucks, or similar). All transactional
email content is built with **React Email** — plain React components where user
values are passed as props and interpolated as ordinary, auto-escaped JSX
expressions. There is no step anywhere in the pipeline where user input is
concatenated into a template source string and then compiled, which is the
precondition SSTI requires. The vulnerability class is structurally absent.

## Deliverable — architecture and evidence

### Email templates are React components, not compiled template strings

`packages/mail/emails/*.tsx` — `Welcome`, `ForgotPassword`, `EmailVerification`,
`MagicLink`, `TelegramOtp`, `DeleteAccountVerification`, `OrganizationInvitation`,
`NewUser`, `NewsletterSignup` — are all `.tsx` React function components,
registered in `packages/mail/emails/index.ts` as `mailTemplates`. No `.hbs`,
`.ejs`, `.mustache`, or other string-template file exists anywhere in the repo.

### Full data flow, traced for the clearest case (a user's display name reaching an email)

1. `packages/auth/auth.ts:512-518` — after signup:
   ```ts
   await sendEmail({
     to: user.email,
     templateId: "welcome",
     context: { name: user.name, url: `${appUrl}/auth/login` },
   });
   ```
2. `packages/mail/util/send.ts` forwards to `getTemplate({ templateId, context, locale })`.
3. `packages/mail/util/templates.ts:18-25`:
   ```ts
   const template = mailTemplates[templateId];
   const email = template({ ...context, locale, translations });
   // ...
   const html = await render(email);
   ```
   `template(...)` here **calls the `Welcome` React function component as a
   function, passing `context` as its props object** — this is a normal React
   render call, not a string-template compilation. There is no step that treats
   `context.name` as part of a template's *source*.
4. `packages/mail/emails/Welcome.tsx:225` — `name` is interpolated as a JSX
   expression child: `Hi {name}, you're one step away from...`. React's
   serializer (`@react-email/render`'s `render()`) HTML-escapes this value the
   same way React always escapes JSX expression children — equivalent in safety
   shape to a parameterized SQL query versus string-concatenated SQL.
5. `render(email)` walks the **already-fully-constructed** React element tree to
   produce the final HTML/plain-text output. At no point does a string
   containing `name` get re-parsed as template syntax.

Every other email template in `packages/mail/emails/` follows this identical
props-based pattern — user-controlled values (name, email, custom messages) are
always passed as props into a statically-defined component tree, never
concatenated into template source.

### No string-template-compilation library exists in the codebase

A repository-wide search found zero usage of `Handlebars.compile`, `ejs.render`,
`nunjucks`, `mustache`, or any comparable engine anywhere in the app.

### Related but out of scope: LLM prompt construction

`packages/ai/lib/prompts.ts` builds prompts for LLM calls using plain JS template
literals, e.g. `` `List me five funny product names for ${topic}` ``. This is
**prompt construction for an external LLM API**, not a document/HTML template
engine — there is no `compile()` step and no template-directive syntax (like
Handlebars' `{{ }}`) exposed to user input that could be escaped out of. This is
more accurately a *prompt injection* consideration (influencing what the LLM is
asked to do) than classical SSTI, and is noted here only for completeness — it
does not affect the verdict for this control, which concerns document/template
compilation specifically.
