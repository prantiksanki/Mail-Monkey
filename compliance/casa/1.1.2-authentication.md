# CASA 1.1.2 — Authentication: Strong password security measures

> **Control 1.1.2 — Authentication / Implement strong password security measures**
>
> *System generated initial passwords or activation codes shall be securely randomly
> generated and expire after a short period.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the initial password or activation code process.
> 3. If a proprietary user authentication service is used by the application, provide
>    screenshots of the initial password or activation code process in action.

---

## Short answer (for the CASA portal)

User authentication is delegated to **Google OAuth 2.0** and the **Microsoft identity
platform (Azure AD) OAuth 2.0** — these are the only sign‑in methods exposed in the
application. The self‑hosted auth layer (Better Auth) issues **no initial passwords,
temporary passwords, or admin‑provisioned credentials**. The only system‑generated
authentication artefacts are email‑verification links, password‑reset tokens, and
2FA one‑time codes. Every one of these is generated with a cryptographically secure
RNG (`crypto.getRandomValues`, rejection‑sampled to remove modulo bias), is
single‑use, and expires between **3 and 60 minutes**.

| Service | Protocol | Where configured | Purpose |
|---------|----------|------------------|---------|
| **Google** (Sign in with Google / Google Identity) | OAuth 2.0 + OpenID Connect | `packages/auth/auth.ts:836` (`socialProviders.google`) | Primary user sign‑in; also authorises Gmail / Calendar scopes |
| **Microsoft identity platform** (Azure AD) | OAuth 2.0 + OpenID Connect | `packages/auth/auth.ts:857` (`socialProviders.microsoft`) | Primary user sign‑in; also authorises Outlook Mail scopes |

These two providers are the **only** authentication options rendered in the UI —
`apps/web/modules/saas/auth/components/LoginForm.tsx` and `SignupForm.tsx` render
only the social sign‑in buttons defined in
`apps/web/modules/saas/auth/constants/oauth-providers.tsx` (`google`, `microsoft`).

**Not user authentication (do not count):** the app also holds optional
`genericOAuth` connectors for **Zoom** and **Zoho Meeting**
(`packages/auth/auth.ts:879`). These are *video‑meeting integrations* — they connect
a third‑party account to an already‑authenticated user and are never used to
establish an application session. They are only registered when their credentials
are present in the environment.

## Deliverable 2 — Proprietary authentication service: initial password / activation code process

### Summary: there is no initial‑password process

The application runs a self‑hosted auth layer, **Better Auth `1.4.7`**
(`packages/auth/package.json`), but it does **not** implement any of the flows this
control targets:

- **No system‑generated initial passwords.** Password‑based login is disabled —
  `packages/auth/config.ts:16` → `enablePasswordLogin: false`. The login and signup
  screens present OAuth only.
- **No administrator‑provisioned credentials.** There is no admin action, script, or
  onboarding flow that sets a starting password for a user. Accounts are created by
  the user completing Google/Microsoft OAuth.
- **No activation‑code enrolment.** New accounts become active by completing OAuth
  (identity already verified by the IdP), not by redeeming a code.
- **Organisation invitations are disabled** — `packages/auth/config.ts:34` →
  `organizations.enable: false` — so the invitation‑token flow is not reachable.

### System‑generated tokens that *do* exist, and why each satisfies 1.1.2

All are created through Better Auth. Random string tokens come from
`@better-auth/utils@0.3.0` → `createRandomStringGenerator` (file
`node_modules/@better-auth/utils/dist/random.mjs`), which draws bytes from
`crypto.getRandomValues` and applies rejection sampling
(`maxValid = Math.floor(256 / charSetLength) * charSetLength`) so there is no
modulo bias. `generateId(n)` (`@better-auth/core` → `utils`) is the same generator
over a 62‑character alphabet.

| Artefact | Trigger | Generation | Entropy | Expiry (Better Auth default, not overridden) | Single‑use | Code reference |
|----------|---------|------------|---------|----------------------------------------------|------------|----------------|
| **Email verification link** | Sign‑up when email verification is on | HS256 JWT signed with the server secret (`BETTER_AUTH_SECRET`); carries an `exp` claim | Unforgeable without the HMAC secret | **3600 s (1 hour)** — `createEmailVerificationToken(..., expiresIn = 3600)` | Yes — guarded by the `emailVerified` flag; a verified address rejects re‑verification | `node_modules/better-auth/dist/api/routes/email-verification.mjs:13`, `:105`, `:252` |
| **Password‑reset token** | User requests a reset (`sendResetPassword`, `packages/auth/auth.ts:803`) | `generateId(24)` — 24 chars over `a‑z A‑Z 0‑9` | ~143 bits | **3600 s (1 hour)** — `resetPasswordTokenExpiresIn ?? 3600` | Yes — row deleted via `deleteVerificationValue` immediately after the password is updated | `node_modules/better-auth/dist/api/routes/reset-password.mjs:61-62`, `:148`, `:158` |
| **Magic‑link token** | *Plugin registered (`packages/auth/auth.ts:883`) but no UI invokes it — currently dormant* | `generateRandomString(32, "a-z", "A-Z")` | ~182 bits | **300 s (5 minutes)** — `expiresIn ?? 300` | Yes — row deleted via `deleteVerificationValue` on use *and* on expiry | `node_modules/better-auth/dist/plugins/magic-link/index.mjs:54`, `:62`, `:120-124` |
| **Two‑factor e‑mail OTP** | 2FA challenge (`twoFactor()` plugin, `packages/auth/auth.ts:928`; `enableTwoFactor: true`) | `generateRandomString(6, "0-9")` | 6 digits, backed by CSPRNG; brute force bounded by 3‑min TTL + single‑use + rate limiting | **180 s (3 minutes)** — `(period ?? 3) * 60 s` | Yes | `node_modules/better-auth/dist/plugins/two-factor/otp/index.mjs:25`, `:72`, `:77` |

**Passkeys** (`packages/auth/config.ts:12` `enablePasskeys: true`; managed from
`apps/web/modules/saas/settings/components/PasskeysBlock.tsx`) are WebAuthn
credentials — the key pair is generated on the user's device and the server never
generates or transmits a secret, so they are outside the scope of this control.

### Token invalidation

Expired or already‑used tokens are rejected on every path:
`reset-password.mjs:116` / `:148` and `magic-link/index.mjs:120` compare
`verification.expiresAt < new Date()` before honouring the token, and delete the
verification row on use.
