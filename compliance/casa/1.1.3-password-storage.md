# CASA 1.1.3 — Authentication: Passwords resistant to offline attacks

> **Control 1.1.3 — Authentication / Implement strong password security measures**
>
> *Passwords shall be stored in a form that is resistant to offline attacks.*
>
> **Deliverables**
> 1. Provide a list of any external user authentication services.
> 2. If a proprietary user authentication service is used by the application, provide
>    a written description of the password storage methods including any cryptographic
>    protections such as salts or hashing.

---

## Short answer (for the CASA portal)

Authentication is delegated to **Google OAuth 2.0** and the **Microsoft identity
platform (Azure AD) OAuth 2.0**; these providers store and verify all end‑user
credentials. Password‑based login is disabled in the application
(`packages/auth/config.ts:16` → `enablePasswordLogin: false`), so no user passwords
are collected or stored in normal operation.

Where a password *is* set (e.g. if password login is re‑enabled), the self‑hosted
auth layer (Better Auth `1.4.7`) stores it only as a **scrypt** hash — a memory‑hard
key‑derivation function — with a unique 128‑bit cryptographically‑random salt per
password. Plaintext and reversible encryption are never used. Parameters:
`N = 16384, r = 16, p = 1, dkLen = 64` (~32 MB memory cost per hash). Verification
is constant‑time.

## Deliverable 1 — External user authentication services

| Service | Protocol | Where configured | Role |
|---------|----------|------------------|------|
| **Google** (Sign in with Google) | OAuth 2.0 + OpenID Connect | `packages/auth/auth.ts:836` (`socialProviders.google`) | Stores & verifies user credentials; only sign‑in method in the UI |
| **Microsoft identity platform** (Azure AD) | OAuth 2.0 + OpenID Connect | `packages/auth/auth.ts:857` (`socialProviders.microsoft`) | Stores & verifies user credentials; only sign‑in method in the UI |

For accounts created via these providers, the `account.password` column is `NULL` —
the application holds **no** credential material for them, only OAuth access /
refresh tokens.

Zoom and Zoho Meeting `genericOAuth` connectors (`packages/auth/auth.ts:879`) are
meeting integrations, not user authentication, and never carry a password.

## Deliverable 2 — Proprietary password storage method

### Current state

Password login is **disabled** — `packages/auth/config.ts:16`
`enablePasswordLogin: false`. The login and signup screens expose OAuth only, so in
normal operation the application does not collect or persist any user password.

### Storage schema

Passwords, when present, live in a single nullable column:

```
model Account {            // packages/database/prisma/schema.prisma:264
  ...
  providerId  String       // "google" | "microsoft" | "credential"
  password    String?      // schema.prisma:274 — null for OAuth accounts
  ...
}
```

There is no other location in the schema that holds credential material. No plaintext
column, no reversibly‑encrypted column.

### Hashing algorithm and cryptographic protections

Better Auth `1.4.7` (pinned in `packages/auth/package.json`) is used with its default
password hasher — the application does **not** override `emailAndPassword.password`
with a custom `hash` / `verify`, so the following applies verbatim
(`node_modules/better-auth/dist/crypto/password.mjs`):

| Property | Value | Notes |
|----------|-------|-------|
| Algorithm | **scrypt** | Memory‑hard KDF, via `@noble/hashes@^2.0.0` (`scryptAsync`). Resistant to GPU / ASIC / FPGA offline cracking. |
| Cost parameters | `N = 16384` (2¹⁴), `r = 16`, `p = 1` | Memory cost ≈ `128 · N · r` ≈ **32 MiB** per hash; `r = 16` is 2× the common default, raising the memory hardness. |
| Derived key length | `dkLen = 64` bytes (512‑bit) | |
| Salt | **16 bytes (128‑bit), unique per password**, from `crypto.getRandomValues` (CSPRNG) | Generated at `hashPassword` time; stored alongside the hash. |
| Stored format | `"<salt_hex>:<derivedKey_hex>"` in `account.password` | Salt is not secret; it is stored with the hash by design. |
| Input normalisation | Unicode **NFKC** before hashing | Consistent hashing of equivalent Unicode strings. |
| Verification | `constantTimeEqual(...)` | Constant‑time comparison of derived keys — no timing side channel. |
| Reversibility | None | One‑way KDF; the plaintext cannot be recovered from storage. |

Source (`node_modules/better-auth/dist/crypto/password.mjs`):

```js
const config = { N: 16384, r: 16, p: 1, dkLen: 64 };

async function generateKey(password, salt) {
  return await scryptAsync(password.normalize("NFKC"), salt, {
    N: config.N, p: config.p, r: config.r, dkLen: config.dkLen,
    maxmem: 128 * config.N * config.r * 2,
  });
}

const hashPassword = async (password) => {
  const salt = hex.encode(crypto.getRandomValues(new Uint8Array(16)));
  const key = await generateKey(password, salt);
  return `${salt}:${hex.encode(key)}`;
};

const verifyPassword = async ({ hash, password }) => {
  const [salt, key] = hash.split(":");
  if (!salt || !key) throw new BetterAuthError("Invalid password hash");
  return constantTimeEqual(await generateKey(password, salt), hexToBytes(key));
};
```

### Password‑reset handling

A reset writes the new password through the same `hashPassword` path
(`internalAdapter.updatePassword`, `node_modules/better-auth/dist/api/routes/reset-password.mjs:157`)
and the single‑use reset token row is deleted immediately afterwards
(`reset-password.mjs:158`). Optionally all sessions are revoked on reset
(`revokeSessionsOnPasswordReset`). No password is ever logged.

### Summary against the control

Passwords are stored only as salted scrypt hashes with per‑password 128‑bit random
salts and memory‑hard parameters (~32 MiB), which is resistant to offline
brute‑force and rainbow‑table attacks. In practice no passwords are stored at all
while `enablePasswordLogin` is `false`.
