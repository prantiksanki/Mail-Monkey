# CASA 4.1.1 — Communications: TLS 1.2+, secure cipher suites

> **Control 4.1.1 — Communications / Protect confidential data through strong
> cryptography**
>
> *Application shall enforce the use of TLS for all connections and default to TLS
> 1.2+. In cases where support for legacy clients is necessary, TLS 1.0 and 1.1 may
> be supported if mitigations are implemented to minimize the risk of downgrade
> attacks and known TLS exploits. Regardless of the TLS version in use, the
> application shall default to secure cipher suites and reject those with known
> vulnerabilities.*
>
> **Deliverable**
> 1. Execute a Qualys SSL Labs scan for the application and provide a PDF export of
>    the test results demonstrating that the application meets the aforementioned
>    TLS requirements. In most cases, this should result in a B or higher score.

---

## Short answer (for the CASA portal)

A Qualys SSL Labs scan of `staging.popsuites.ai` (Azure App Service, Central India)
returned an **A+** overall rating — well above the B threshold. Only TLS 1.3 and TLS
1.2 are offered; TLS 1.1, TLS 1.0, and SSL 3/2 are all disabled. The server-preferred
cipher order puts strong, forward-secret AEAD suites first. No known TLS
vulnerability (Heartbleed, POODLE, ROBOT, CCS injection, RC4, compression/CRIME) was
found, and HSTS is deployed with a 2-year `max-age` and `includeSubDomains`.

### Protocols

| Protocol | Supported |
|---|---|
| TLS 1.3 | Yes |
| TLS 1.2 | Yes |
| TLS 1.1 | **No** |
| TLS 1.0 | **No** |
| SSL 3 | No |
| SSL 2 | No |

Only TLS 1.2+ is offered — no legacy-client fallback is enabled, so the control's
"if TLS 1.0/1.1 are supported, mitigations are required" branch doesn't apply here.

### Cipher suites (server-preferred order)

TLS 1.3 offers only the two modern AEAD suites (`TLS_AES_256_GCM_SHA384`,
`TLS_AES_128_GCM_SHA256`). TLS 1.2 lists the ECDHE+GCM (forward-secret, strong)
suites first, followed by legacy CBC/non-forward-secret suites that Qualys flags
"WEAK" (offered for compatibility with older clients that can't negotiate
TLS 1.3/GCM, but ranked last so any modern client — effectively all real traffic —
negotiates a strong suite). No suite uses RC4, and no anonymous or export-grade
cipher is offered.

### Known-vulnerability checks — all clear

| Check | Result |
|---|---|
| Heartbleed | No |
| POODLE (SSLv3 / TLS) | No |
| ROBOT | No |
| OpenSSL CCS (CVE-2014-0224) | No |
| OpenSSL Padding Oracle (CVE-2016-2107) | No |
| RC4 | No |
| SSL/TLS compression (CRIME) | No |
| Ticketbleed | No |
| Downgrade protection (`TLS_FALLBACK_SCSV`) | Not supported — informational only; not exploitable given TLS 1.0/1.1 are already disabled server-side, so there is no lower-strength protocol for a downgrade attack to fall back to |
| BEAST | Mitigated server-side |

### Certificate and transport hardening

- Certificate: RSA 2048-bit, SHA-256 signature, valid chain to DigiCert Global Root
  G2, not revoked, Certificate Transparency present.
- **HSTS:** `Strict-Transport-Security: max-age=63072000; includeSubDomains` —
  matches `apps/web/next.config.ts:141-143` (`strictTransportSecurity` constant).
  Not submitted to browser preload lists, which is a minor durability
  recommendation, not a control requirement.
- OCSP stapling: enabled.
- Forward secrecy: yes, with all modern reference clients.

### Note on hosting/config ownership

TLS termination and the protocol/cipher floor are managed by Azure App Service
platform defaults for this deployment — there is no `minTlsVersion` setting or other
TLS configuration codified in this repository (no Bicep/ARM/Terraform provisions
either App Service resource). The scan confirms the *current* effective
configuration meets the control; because that configuration isn't version-controlled,
it should be re-verified after any change to the App Service resource (e.g. a portal
edit, a new deployment slot, or a custom-domain/cert change).
