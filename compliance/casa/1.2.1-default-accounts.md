# CASA 1.2.1 — Authentication: Disable default accounts on public interfaces

> **Control 1.2.1 — Authentication / Disable any default accounts for public
> application access interfaces**
>
> *Default credentials shall not be present on publicly exposed interfaces.*
>
> **Deliverables**
> 1. If any default accounts are present on publicly exposed interfaces, a
>    confirmation that default credentials are not used shall be provided.

---

## What this control means

Software often ships with built‑in accounts that have a known or guessable password
— `admin/admin`, a seeded superuser, a demo login, a sample API key, a framework
default. This control requires assurance that no such account with its **default
credential still active** can authenticate against any internet‑facing interface
(the web app, an admin panel, the API, a metrics/monitoring endpoint, a database
console, etc.).

---

## Confirmation statement (for the CASA portal)

**The application ships with no default accounts and no default credentials on any
publicly exposed interface.**

- The only public authentication interface (`/auth/login`, `/auth/signup`) uses
  **Google** and **Microsoft** OAuth 2.0 exclusively. There is no built‑in local
  login, and no user records are pre‑created.
- There is **no database seeding**. The `@repo/database` package defines no
  `prisma db seed` script, and no migration or deploy step creates any account.
- No account, API key, or secret is hardcoded anywhere in the application or
  infrastructure code. All credentials are supplied at runtime via environment
  variables; the committed `.env.local.example` contains only placeholder values
  (`A_RANDOM_SECRET_STRING`, `YOUR_GOOGLE_CLIENT_SECRET`, empty strings).
- The `admin` role exists (Better Auth `admin()` plugin) but **no admin user is
  pre‑provisioned**. The `admin` role is granted manually to a real,
  OAuth‑authenticated user.

---

## Deliverable 1 — details and evidence

### Public interface: no local accounts

`apps/web/modules/saas/auth/components/LoginForm.tsx` / `SignupForm.tsx` render only
the Google and Microsoft OAuth buttons. Password login is disabled
(`packages/auth/config.ts:16` → `enablePasswordLogin: false`). No seeded or default
user is present to authenticate as.

### No seeding on deploy

- `packages/database/package.json` — no `seed` / `db:seed` script, no
  `prisma.seed` key.
- Repo‑wide search for `prisma db seed` / `"seed"` in `package.json` files: no
  match.

### Operator provisioning script — not a default account, not exposed

`tooling/scripts/src/create-user.ts` is an **interactive CLI**, run manually by an
operator with database access. It is not part of the deployed application and has no
network interface. It does **not** use a fixed or default password:

```ts
const adminPassword = nanoid(16);                       // fresh random per run
const hashedPassword = await authContext.password.hash(adminPassword);  // scrypt
...
logger.info(`Here is the password for the new user: ${adminPassword}`); // shown once
```

`admin@example.com` / `Adam Admin` in the file are **input placeholders** for the
prompts, not values that get created.

### Test seed helper — test database only

`packages/api/test-helpers/db-seed.ts` runs only during `pnpm test` against a
disposable test database. It creates users on the `@zeromail-test.invalid` domain
with **no password set** (`providerId: "google"`, no `hashedPassword`) and deletes
them in `teardownTestSeed`. It is never executed in staging or production.

### Infrastructure / non‑UI endpoints

- `infra/alloy/config.alloy` — the metrics scrape uses
  `bearer_token = env("METRICS_SCRAPE_TOKEN")` and Grafana Cloud push uses
  `basic_auth` with `env("GRAFANA_CLOUD_USERNAME")` / `env("GRAFANA_CLOUD_PASSWORD")`.
  All from environment variables; no hardcoded or default value.
- `apps/web/app/api/metrics/route.ts` — requires the `METRICS_SCRAPE_TOKEN` bearer
  token; there is no default token, and no username/password account is involved.
