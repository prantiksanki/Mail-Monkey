# CASA 6.3.1 — Configuration: Origin header not used for access control

> **Control 6.3.1 — Configuration**
>
> *The origin header shall not be used for authentication of access control
> decisions.*
>
> **Deliverable**
> 1. Testing results from a scan completed using the ADA's Dynamic Application
>    Security Testing Guidance. Scanning may be performed by the developer or by
>    an authorized testing lab.

---

## Why this matters

The `Origin` (and `Referer`) HTTP header is set entirely by the client and is
not cryptographically bound to anything. A browser sets it automatically for
cross-origin requests, but a non-browser client — `curl`, a script, a
modified request — can set it to any value at all. Using it as a substitute
for real authentication (a session token, an API key, a verified credential)
is a bypassable access-control decision: an attacker who wants access simply
sends the header value the check expects.

---

## Short answer (for the CASA portal)

No application code in this codebase reads the `Origin` or `Referer` header
to make an authentication or authorization decision. Origin is used in
exactly two legitimate, standard ways: as a **static** CORS allowlist value
(not reflected from the request), and by Better Auth's built-in
`trustedOrigins` mechanism to validate redirect-target *parameters* as a
CSRF/open-redirect defense — layered on top of, never instead of, real
session authentication.

---

## Deliverable — evidence

### No application code reads Origin/Referer for an auth decision

A repository-wide search across `apps/web`, `packages/api`, and
`packages/auth` for `headers.get("origin")`, `c.req.header("origin")`, and
equivalent patterns found **zero matches** in application code. Origin is
only touched internally by framework/middleware layers (Hono's `cors()`,
Better Auth's `originCheckMiddleware`) — no procedure, route handler, or
middleware in this codebase reads the raw header value itself to grant or
deny a request.

### CORS configuration — a static allowlist, not a reflected Origin check

`packages/api/index.ts:129-137`:

```ts
.use(
  cors({
    origin: getBaseUrl(),
    allowHeaders: ["Content-Type", "Authorization"],
    allowMethods: ["POST", "GET", "OPTIONS"],
    exposeHeaders: ["Content-Length"],
    maxAge: 600,
    credentials: true,
  }),
)
```

`origin` is set to `getBaseUrl()` — a **static string** resolved once from
environment configuration (the app's own deployed URL), not a function that
reads and echoes the incoming request's `Origin` header. This is the safe
CORS pattern: Hono's `cors()` middleware sends
`Access-Control-Allow-Origin` matching only that fixed value; a request from
any other origin receives no CORS headers at all. This specifically rules
out the classic dangerous misconfiguration — reflecting *any* client-supplied
Origin back combined with `credentials: true`, which would let an arbitrary
website make authenticated, credentialed requests against this API on a
victim's behalf. CORS itself is a browser-enforced same-origin *relaxation*
mechanism, not an authentication mechanism — this app correctly relies on
session cookies/tokens for the actual authentication, with CORS only
controlling which browser-origin JavaScript is allowed to read the response.

### Better Auth's `trustedOrigins` — CSRF defense, not an auth substitute

`packages/auth/auth.ts`'s `trustedOrigins: [appUrl, ...extraTrustedOrigins]`
feeds Better Auth's `originCheckMiddleware`, which validates the
`callbackURL`/`redirectTo` *request parameters* (not a decision to
authenticate the request itself) against that trust list before allowing a
redirect. This was already confirmed under
[`5.1.2`](./5.1.2-open-redirect.md) as legitimate CSRF/open-redirect
mitigation — it runs on top of, and after, real session/credential
verification; it never substitutes for it. A request still needs a valid
session or a legitimate OAuth flow in progress regardless of what
`trustedOrigins` allows.

### Referer / referrer-policy — output hardening, not an input trust decision

Every `Referer`-adjacent occurrence in the codebase is either the unrelated
`rel="noopener noreferrer"` link attribute, `referrerPolicy="no-referrer"` on
iframes/images (`InboxPage.tsx`, `PaymentDetailDialog.tsx` — prevents the
app's own URL from leaking to embedded third-party content the user is
viewing), or the outbound `Referrer-Policy: strict-origin-when-cross-origin`
response header (`apps/web/next.config.ts`). None of these read the inbound
`Referer` header to grant or deny access to anything — they all control what
this app discloses to *other* sites, not what it trusts from incoming
requests.

### Not applicable: client-supplied headers used for rate limiting

`packages/api/lib/rate-limit.ts`'s `getClientIp` reads
`x-azure-clientip`/`x-forwarded-for`/`x-real-ip` (proxy/client-supplied
headers) purely as a bucketing key for rate limiting — not as an
authentication or authorization signal. Spoofing these headers only lets an
attacker land in a different rate-limit bucket (evading their own throttle);
it never grants access to a protected resource or elevates privilege. This
is unrelated to `Origin` specifically and out of scope for this control's
authentication framing.

### On the listed deliverable (DAST scan)

As with the preceding 5.x/6.x controls, the checklist's deliverable text
calls for an external dynamic scan, tracked as the same open item under
[`3.1.1`](./3.1.1-urls-no-auth-material.md). Since no code path here uses
Origin as an authentication mechanism, a DAST scan attempting to bypass auth
via a forged `Origin` header should find nothing to exploit.
