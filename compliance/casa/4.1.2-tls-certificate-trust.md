# CASA 4.1.2 — Communications: Trusted TLS certificates on all connections

> **Control 4.1.2 — Communications / Protect confidential data through strong
> cryptography**
>
> *Connections to and from the server shall use trusted TLS certificates. Where
> internally generated or self-signed certificates are used, the server must be
> configured to only trust specific internal CAs and specific self-signed
> certificates. All others should be rejected.*

---

## A note on the listed deliverable

The checklist's deliverable text for this row ("Execute a Qualys SSL Labs scan...")
is carried over from control 4.1.1 and doesn't actually test what 4.1.2 asks about.
Qualys SSL Labs scans the server's **own** inbound TLS configuration (protocol
versions, cipher suites, the server's certificate) — see
[`4.1.1-tls-configuration.md`](./4.1.1-tls-configuration.md) for that result (A+).
It cannot observe whether the *server itself*, acting as a client, correctly
validates the certificates of the systems **it** connects to (the database,
third-party APIs). That's what this control is actually about, and it can only be
answered by auditing the code and configuration that establishes those outbound
connections — which is what follows.

---

## Short answer (for the CASA portal)

No code in this application disables or weakens TLS certificate validation on any
connection, inbound or outbound. A full-repository audit found zero occurrences of
`rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, `strictSSL: false`,
custom CA trust overrides, or any insecure HTTP client configuration. Every outbound
integration uses the platform's default (certificate-validating) `fetch` or an
official provider SDK. The one item not verifiable from source code — the Postgres
connection's `sslmode` — is called out below with a recommendation.

---

## Findings

### 1. No disabled/weakened certificate validation anywhere

Searched the full repository (application code, CI workflows, the one Dockerfile at
`infra/alloy/Dockerfile`) for every common way TLS verification gets weakened:

| Pattern searched | Result |
|---|---|
| `rejectUnauthorized: false` / `= false` | No matches |
| `NODE_TLS_REJECT_UNAUTHORIZED` (any value) | No matches |
| `ssl: false` / `ssl: { rejectUnauthorized` | No matches |
| `strictSSL: false` | No matches |
| Custom `ca:` (CA override) in an HTTP client | No matches |
| `NODE_EXTRA_CA_CERTS` | No matches |
| `--insecure` flag | No matches |
| `insecure` (any case) | 2 matches, both false positives: `.claude/agents/security-auditor.md:13` ("Insecure direct object references", unrelated prose) and `apps/web/proxy.ts:82` (`upgrade-insecure-requests` CSP directive, which *forces* HTTPS upgrades — strengthens, not weakens) |

### 2. Outbound third-party integrations

Every integration that makes an outbound HTTPS call — Google OAuth, Microsoft
identity platform, Zoom, Zoho Meeting, Stripe/Creem, AWS SES, Plunk, Postmark, the
Telegram Bot API, Sequenzy — uses either the platform default `fetch` (Node/undici,
which validates certificates against the system trust store by default) or an
official provider SDK. No file in the repo constructs a custom `https.Agent` or
`undici.Agent` with TLS options, so nothing overrides or narrows the default trust
store to a specific internal CA or self-signed certificate — meaning the "internal
CA / self-signed" branch of this control's requirement doesn't apply here: this
application doesn't use internally-generated or self-signed certificates for any
connection it makes.

### 3. Database connection — the one gap not visible from code

`packages/database/prisma/client.ts:9-11` constructs the Postgres adapter as:

```ts
const adapter = new PrismaPg({
  connectionString: process.env.DATABASE_URL,
});
```

and `packages/database/drizzle/client.ts:13` similarly passes `DATABASE_URL`
straight through with no explicit SSL options object. Both delegate entirely to
`node-postgres`'s own connection-string parsing, meaning the connection's TLS/cert
behavior is determined solely by whatever `sslmode` (or `ssl=true`/`ssl=false`)
parameter is embedded in the actual `DATABASE_URL` value — which lives in Azure App
Service / CI secrets, not in this repository, and so cannot be confirmed by reading
code. `.env.local.example` gives no guidance on this parameter either.

**This is not a finding of insecure behavior** — nothing in the repo hardcodes
`sslmode=disable`, `sslmode=allow`, or `sslmode=no-verify` — but it is unasserted:
a connection string without an explicit, verifying `sslmode` could silently accept
an untrusted certificate on the database connection, and there is currently nothing
in code or repo configuration that would catch that.

**Recommendation:** confirm the production and staging `DATABASE_URL` values use
`sslmode=require` at minimum, or `sslmode=verify-full` for full hostname + CA
verification if the Postgres provider supports it (Azure Database for PostgreSQL
does). Consider adding a `# Ensure sslmode=require or verify-full` comment next to
`DATABASE_URL` in `.env.local.example` so this isn't rediscovered from scratch on
the next audit.
