# CASA 6.1.1 — Configuration: Keep all components up to date

> **Control 6.1.1 — Configuration / Keep all components up to date**
>
> *The application only uses software components without known exploitable
> vulnerabilities.*
>
> **Deliverable**
> 1. Provide output of a dependency scan of application and 3P libraries using
>    OWASP dependency check or other ADA approved scanning tools.

---

## Short answer (for the CASA portal)

`pnpm audit` (the workspace's native dependency-vulnerability scanner, equivalent
in purpose to `npm audit`/OWASP dependency-check) was run against the full
monorepo lockfile. Of 328 reported advisories, the six that traced to direct,
production-reachable dependencies with critical/high severity have been
upgraded to patched versions. The remainder trace to dev-only tooling
(build scripts, test helpers, internal preview/docs apps) or a confirmed-dead
code path, and are documented below rather than fixed, since they carry no
runtime exposure. One dependency (`better-auth`) has additional fixes only
available in a later minor version, tracked as a prioritized follow-up.

## Deliverable — scan process and results

### How to reproduce this scan

```bash
pnpm audit --json > audit-output.json
pnpm audit   # human-readable summary
```

Run from the repository root; `pnpm audit` checks every dependency across all
workspace packages against the npm advisory database.

### Raw result (before remediation)

328 advisories across 1,776 resolved dependencies: 9 critical, 129 high, 162
moderate, 28 low.

### Fixed — direct, production-reachable, patched in this pass

| Package | Before | After | Severity | Issue |
|---|---|---|---|---|
| `better-auth` | 1.4.7 | **1.4.22** | CRITICAL | Two-factor authentication bypass via premature session caching (`session.cookieCache`) |
| `@orpc/client` | 1.13.2 | **1.13.14** | CRITICAL | Prototype pollution via `StandardRPCJsonSerializer` deserialization |
| `@orpc/openapi` | 1.13.2 | **1.13.14** | HIGH | Stored XSS in OpenAPI Reference Plugin via unescaped `JSON.stringify` |
| `hono` | 4.11.7 | **4.13.7** | HIGH | CORS middleware reflects any Origin with credentials when `origin` defaults to wildcard |
| `js-cookie` | 3.0.5 | **3.0.8** | HIGH | Per-instance prototype hijack in `assign()` enabling cookie-attribute injection |
| `sharp` | 0.34.5 | **0.35.4** | HIGH | Inherited libvips/libheif CVEs |

Sibling oRPC packages (`@orpc/tanstack-query`, `@orpc/json-schema`,
`@orpc/server`, `@orpc/zod`) and `@better-auth/passkey` were bumped in
lockstep to matching versions to satisfy peer-dependency constraints.

**Fallout from the upgrade, found and fixed:**
- The lockfile re-resolution introduced a second `zod` instance
  (`4.6.1`, pulled in transitively by updated `fumadocs-*` packages used by
  the internal docs app) alongside the application's pinned `zod@4.3.6`,
  which confused `@hookform/resolvers`' generic type inference across 5
  files (`ChangeEmailForm.tsx`, `ChangeNameForm.tsx`, `ChangePassword.tsx`,
  `CreatorModeForm.tsx`, and the underlying form-schema types). Fixed by
  adding `pnpm.overrides: { "zod": "4.3.6" }` to the root `package.json`,
  pinning a single resolved `zod` version workspace-wide.
- `better-auth`'s updated types made `packages/auth/plugins/invitation-only/index.ts`'s
  `context.path` possibly `undefined` (a stricter/more accurate type in the
  new version) — fixed with an optional-chaining guard.
- `packages/api/modules/mailboxes/lib/microsoft-auth.test.ts` predated this
  session's OAuth-token-encryption work (see
  [`4.1.3`](./4.1.3-cryptographic-operations.md)) and used plaintext token
  fixtures that failed `decryptToken`'s format validation once the full test
  suite was actually run end-to-end. Fixed by mocking `@repo/utils`'s
  encrypt/decrypt as identity functions in that suite, since it tests OAuth
  refresh logic, not encryption (which has its own coverage).

**Verified:** re-ran `pnpm audit` after the upgrade — all six advisories above
no longer appear for the upgraded versions (the same advisory titles still
appear in the report, but only against confirmed dev-tooling/dead-code
paths — see below). `pnpm --filter web type-check`, `pnpm --filter @repo/auth
type-check`, and `pnpm --filter @repo/database type-check` are clean (only
pre-existing, unrelated errors remain — see [`6.2.1`](./6.2.1-debug-mode.md)
for the pre-existing-error baseline established this session). The full
`@repo/api` test suite (179 tests) passes.

### Deferred, with reason — follow-up items

- **`protobufjs`** (critical) via `packages__api>@xenova/transformers>onnxruntime-web`
  — **Resolved 2026-09-12:** `@xenova/transformers` (Whisper transcription)
  and `node-llama-cpp` (TinyLlama free-tier generation) were removed
  entirely and replaced with calls to the hosted Sarvam API — see
  `packages/ai/lib/sarvam.ts`. This dependency, and the `protobufjs`
  advisory that rode along with it, no longer exist in the tree.
- **`better-auth` — remaining advisories only fixed in 1.6.x.** After
  upgrading to `1.4.22` (which resolves the original critical 2FA-bypass
  finding), a re-scan surfaced further real issues in the `better-auth`
  dependency tree that are **not yet fixed at any 1.4.x release** — they
  require the `1.6.x` line:

  | Severity | Issue | Fixed in |
  |---|---|---|
  | CRITICAL | OAuth refresh-token replay via missing client authentication on `oidc-provider`/`mcp` plugins | ≥1.6.11 |
  | HIGH | Account takeover via pre-account hijacking on magic-link and email-OTP sign-in | ≥1.6.22 |
  | HIGH | Unauthorized invitation acceptance via unverified email match in organization plugin | ≥1.6.11 |
  | HIGH | Insecure cryptographic defaults in `oidcProvider` (`alg=none` advertised, plain PKCE accepted) | ≥1.6.11 |
  | HIGH | Stored XSS in the auth-server origin via `javascript:` `redirect_uri` in `oidc-provider`/`mcp` | ≥1.6.13 |
  | HIGH | OAuth authorization-code grant allows concurrent redemption (race in find-then-delete) | ≥1.6.11 |
  | HIGH | OAuth refresh-token rotation forks the token family on concurrent redemption | ≥1.6.0 |
  | MODERATE | OAuth callback accepts mismatched `state` when cookie-backed state storage is used without PKCE | ≥1.6.2 |
  | LOW | Stale sessions persist after user deletion across admin/anonymous/SCIM flows | ≥1.6.11 |

  A `1.4→1.6` jump is a minor-version migration with real potential for
  breaking changes in `better-auth`'s own behavior, not a narrow patch bump —
  this was confirmed with the user as **out of scope for this pass** and
  needs its own dedicated upgrade-and-test cycle given `better-auth` is the
  most security-sensitive dependency in the application.

  **Reachability check (done in this pass):** `packages/auth/auth.ts` was
  searched for `oidcProvider`/`mcp` plugin registration — **neither is
  present**. This app only registers `admin`, `organization`, `twoFactor`,
  `magicLink`, `passkey`, `username`, `openAPI`, `genericOAuth`, and the
  custom `invitationOnlyPlugin`. The CRITICAL finding (OAuth refresh-token
  replay) and several of the HIGH findings above are scoped specifically to
  the `oidc-provider`/`mcp` plugins, so **they are very likely not reachable
  in this deployment today**.

  **The finding that IS directly relevant to this app's real auth surface:**
  the magic-link/email-OTP pre-account-hijacking account-takeover issue
  (HIGH, vulnerable `>=1.1.3 <1.6.22`, so still present at `1.4.22`) —
  `magicLink` is a registered plugin in this app's config (confirmed earlier
  this session, though the UI doesn't currently expose a magic-link entry
  point — see [`1.3.1`](./1.3.1-oob-verifiers.md)). Since the plugin is
  registered and reachable at the API level even without a UI affordance,
  this is the **actual highest-priority item** in the `1.6.x` follow-up,
  ranked above the OAuth-replay critical given the latter's plugins aren't
  even enabled here.

## Re-scan — 2026-09-12

Fresh `pnpm audit` run against the current lockfile (branch `main`) to produce a
current-dated scan output for the CASA portal submission (evidence index F3). PDF +
raw JSON/text output saved to
`~/Desktop/CASA-6.1.1-Dependency-Scan-2026-09-12.{pdf,html}` and
`~/Desktop/dependency-scan-2026-09-12.{json,txt}` (kept outside this repo per this
folder's convention).

**301 advisories** (245 distinct): 8 critical, 133 high, 135 moderate, 25 low,
across 1,811 resolved dependencies.

- **Re-verified fixed:** all six advisories patched in the 2026-09-11 pass
  (`better-auth`, `@orpc/client`, `@orpc/openapi`, `hono`, `js-cookie`, `sharp`) are
  confirmed still patched at their pinned versions — remaining findings against
  those package names trace only to separate, nested copies pulled in by unrelated
  dev tooling.
- **`drizzle-orm` (`packages/database`) confirmed dead code:** `packages/database/index.ts`
  exports only `./prisma` — the `packages/database/drizzle/` tree is never imported
  anywhere else in the workspace. Moved from "documented, not fixed" to "confirmed
  dead code," same treatment as the S3 provider.
- **Two new items surfaced, not covered in the 2026-09-11 pass:**
  - **`nodemailer`** (`packages/mail`, pinned `^7.0.10`) — 2 HIGH advisories, both
    requiring `>=9.1.0` (a two-major-version jump). The arbitrary-file-read/SSRF
    vector (via the `raw` message option) is not reachable — grepped
    `packages/mail` for `raw:` usage, none found. The quadratic-time DoS in
    address-list parsing is not ruled out, since `packages/mail/provider/nodemailer.ts`
    does pass recipient/sender addresses through nodemailer's parser. **Follow-up:**
    schedule the 7→9 upgrade with regression testing of the mail-send path before
    merging — this is core product functionality, not a narrow patch bump.
  - **`googleapis>gaxios>rimraf>glob>minimatch`/`brace-expansion`** (`packages/api`)
    — 6 HIGH ReDoS/DoS advisories. Confirmed `gaxios` (a real runtime dependency of
    `googleapis`, used for Gmail/Calendar API calls) lists `rimraf` as a genuine
    dependency in its own `package.json`, not just dev tooling. These are ReDoS
    bugs requiring attacker-controlled glob *patterns*; nothing in this app's usage
    of the Gmail/Calendar API passes request input into a glob-matching call, so
    reachability is assessed as low — but flagged here rather than asserted dead,
    since (unlike the S3 provider) this sits inside a package the app actively
    calls in production.
- All other previously-documented buckets (dev/build-time tooling, internal
  `apps/docs`/`apps/mail-preview` tooling, the `protobufjs`/`@xenova/transformers`
  deferral, and the `better-auth` 1.6.x follow-up) are unchanged in status; higher
  counts against them reflect newly-published advisories against those same
  unused/dev-only trees (e.g. new Next.js RCE/DoS CVEs against `apps/docs`'s and
  `apps/mail-preview`'s own `next` copies), not new exposure in the deployed app.
